### 5.1 ADR-0007 与 ADR-0009 / pgvector 的冲突

#### 冲突定性（关键：先分清「禁止的是什么」）

| ADR | 原文要点 | 与本次实现的关系 |
| --- | --- | --- |
| **ADR-0007** | Decision：**做 RAG，但不引向量数据库**；embedding 存 BLOB，进程内余弦。<br>反转条件：**当单用户资料总量达到数千切片、或需要跨资料联合检索时，重新评估引入向量库。** | 我们已落地**跨文档检索**（`kb_retrieval.retrieve_by_scope`）→ **反转条件已被触发**；且 pgvector 改变了「存 BLOB + 进程内余弦」的技术形态 |
| **ADR-0009** Decision 3 | 需要检索层能力时复用 `kb_retrieval` 混合检索 + RRF，**而非引入 LangChain 的 `PGVector`/`EnsembleRetriever`** | 本次实现用**裸 SQL + pgvector 扩展**，未引入 LangChain 的 `PGVector` 抽象 → **与 ADR-0009 不冲突**（反而符合其「复用 kb_retrieval」要求，分发逻辑就写在 `kb_retrieval` 内） |

> **结论**：真正的冲突对象只有 **ADR-0007**，且它自己预留了反转条件。ADR-0009 禁止的是 *LangChain 的 PGVector 封装*，不是 *pgvector 扩展本身*——这一点必须先写清楚，否则会误判为「ADR-0009 被违反」。

#### 冲突的实质：pgvector 是「向量数据库」吗？

| 维度 | Chroma（ADR-0007 禁止的） | pgvector（本次采用） |
| --- | --- | --- |
| 部署形态 | **独立服务**，额外持久化目录与运维 | PostgreSQL **扩展**，随库启停，无独立部署 |
| 数据一致性 | 与业务库双写、需同步 | 与 `document_chunks` 同表同事务 |
| 权限模型 | 需重建 `candidate_id` 隔离 | 沿用现有 `candidate_id` 过滤 |
| 适用规模 | 百万切片 | 单用户数千～数十万切片 |

→ pgvector **不是** ADR-0007 所禁止的「独立向量数据库」，但它确实改变了检索实现路径，**属于必须声明的架构变更**，不能静默覆盖。

#### 最终裁决（2026-05-26，用户决策）：**删除 ADR-0007，明确引入向量库**

不做 superseded 保留，**直接删除文件并清理全部引用**。

### 5.2 T14：「迁移」vs「新增列」的决策

#### 事实

- 工单原文：`document_chunks.embedding` **改** `VECTOR(1024)`
- 实际实现：**新增** `embedding_vec VECTOR(1024)` 列，旧 `embedding`（`LargeBinary`）保留
- 检索：`retrieve_by_scope` 按方言分发 —— PG 走 `embedding_vec` + HNSW；SQLite/dev 走 `embedding` + 内存 numpy

#### 为什么选择了「新增列」（当时的理由）

1. **SQLite 无法表达 `VECTOR` 类型**：dev/test 全量走 SQLite，若直接改列类型，`create_all` 与全部本地测试会立刻崩。
2. **可回滚**：新增列 + `IF NOT EXISTS` 的迁移可安全 downgrade；改列类型一旦在大表上执行，回滚代价高。
3. **双路并存需要两份数据**：内存路径要 bytes，PG 路径要 vector，二者无法共用同一列的存储形态。

#### 真实代价（必须承认）

| 代价 | 说明 | 状态 |
| --- | --- | --- |
| 双写必须同步 | 新资料只写 `embedding` 会让 `embedding_vec` 恒 NULL，而检索 SQL 带 `embedding_vec IS NOT NULL` → **生产检索静默返空** | **已修复**（`documents.py` 在 PG 上同步写两列） |
| 存储翻倍 | 同一向量存两份（1024 维 ≈ 4KB/切片） | 可接受（数十万切片 ≈ 数百 MB） |
| schema 漂移风险 | 迁移建的列曾未进 `models.py`，`create_all` 会缺列、autogenerate 会提议 DROP | **已修复**（`models.py` 加 `embedding_vec`，用 `with_variant(LargeBinary,"sqlite")`） |
| 语义偏离工单 | 「改」变成「加」 | 需收敛（下方方案） |

#### 解决方案

**短期（推荐，本次即采纳）**：接受「新增列」形态，**反向修订工单 14 与 ADR-0010 的措辞**——把目标从「`embedding` 改 `VECTOR(1024)`」改为「在 PG 上以 `embedding_vec` 承载向量检索，`embedding` 保留为 dev/SQLite 与降级路径」。理由：该形态是**同时支持 SQLite dev 与 PG 生产**的唯一低风险解，且已通过端到端验证。

**长期（可选，新增工单）**：当生产确认只跑 PG、不再需要 SQLite 路径时，做一次真迁移：
1. 确认全量 `embedding_vec` 已回填
2. `ALTER TABLE document_chunks DROP COLUMN embedding`
3. 模型删除 `embedding`，`embedding_vec` 更名为 `embedding`
4. 全量测试 + 灰度

触发条件：生产稳定跑 PG 满一个迭代周期，且无回滚需求。

### 5.3 T15：`source_chunk` 仅存 top-1 的取舍

#### 事实

三处写入点均为同一形态：

```python
source_chunk=picked[0]["content"] if picked else None,
```

- `kb_generate.py:178`、`:197`
- `kb_graph.py:123`、`:143`、`:189`

即：**一个批次召回 top-k（k=8）切片，但该批次生成的全部题目共享 `picked[0]` 的内容**。

#### 影响

工单 15 要求「写入生成所依据的 top 切片片段（供回溯溯源）」。实际：

- 题目很可能源自 `picked[3]` 或 `picked[7]`，但溯源一律指向 `picked[0]`
- 对「回溯到原文」这一目的：**能定位到大致范围（该批次召回区间的首片），但可能指错具体切片** → 溯源**可用但不精确**
- 不阻断功能（接口、顺序、鉴权均正常），属**质量折扣**而非缺陷

#### 根因

LLM 批量出题时，一次返回 N 道题，**并未声明每题依据哪个切片**；当前按批写溯源，只能取批级代表。

#### 解决方案（三选一，推荐 B）

| 方案 | 做法 | 精度 | 成本 | 风险 |
| --- | --- | --- | --- | --- |
| A. 提示词要求模型回传 `source_seq` | prompt 增加「每题输出所依据片段的 `seq`」，解析后逐题写 `source_chunk` | **高**（逐题精确） | 中（改 prompt + 解析 + 校验） | 模型可能不遵守，需兜底 |
| **B. 存批级切片清单（推荐）** | `source_chunk` 改为存 `picked` 的 `seq` 列表 JSON（如 `[12,35,88,201]`），前端按需取内容 | 中（精确到批，不再误导指向单一首片） | **低**（仅改写入端） | 字段语义由「文本」变「seq 列表」，需同步 schema 注释与前端 |
| C. 批大小降为 1（每题单独召回） | 每题独占一批 | 高 | **高**（LLM 调用 ×N，成本爆炸） | 成本不可接受 |

**推荐 B**：改动最小、零额外 LLM 成本、消除「指错切片」的误导；若后续需要逐题精度，再以 A 追加（届时可平滑升级，因为 B 已保留批级 seq 集合）。

若坚持保留当前「存文本」语义，也可采用 **B′**：把 `picked` 全部内容拼接后截断存入（如取前 3 片 × 200 字），同样能避免「只指向首片」的误导，且不动字段类型。
