# 检索：保留 RAG，但不引入向量数据库

## Status

superseded by ADR-0010（2026-05-26）｜ 反转条件已触发：跨文档检索（`kb_retrieval.retrieve_by_scope`）已落地，PostgreSQL 生产库改用 pgvector 扩展承载向量检索；单文档内存检索路径保留为 dev/SQLite 默认

> **本 ADR 原文保留以存档决策理由，当前结论以 [ADR-0010](./0010-跨文档检索改用pgvector扩展.md) 为准。**
>
> 精确口径：本 ADR 禁止的是 **Chroma 这类独立部署的向量数据库服务**，该判断**依然成立且未被推翻**；ADR-0010 采用的是 **pgvector（PostgreSQL 扩展，非独立服务）**，仅改变存储与检索路径，不引入额外部署。dev/test 的 SQLite 仍走本 ADR 的内存余弦路径。

## Context

需求文档 8.1 原定「MySQL + 向量库（Chroma 或同类）」用于 RAG 知识库。但本产品的检索范围是**单个文档**：一份资料 200 页 ≈ 200 个切片，200×1024 维暴力余弦在毫秒级完成。

Chroma 是为全库百万切片量级设计的，在此规模下属过度工程，还会带来独立的持久化目录与部署复杂度。

但完全不做检索也不行：切片全量喂入会浪费 token（成本不可控），且「按知识点出题」需要语义召回；同时 PDF 常无可靠标题结构，无法只靠章节过滤。

## Decision

**做 RAG，但不引向量数据库**：切片 embedding 存 `document_chunks.embedding`（BLOB），检索时在进程内做余弦相似度。

## Considered Options

- **全量喂长上下文**（放弃）：输入 token 浪费、成本不可控，长文档还会被截断。
- **引入 Chroma**（放弃）：规模不匹配，部署与维护成本高于收益。
- **纯关键词检索**（放弃）：「教师的权利」这类查询在原文中字面不出现时召回差。
- **文档级内存向量检索 + 关键词/均匀采样降级**（采用）。

## Consequences

- **三级降级**：向量检索 → 关键词检索 → 均匀采样。任一层失效都不得阻塞出题——embedding 失败只把切片标记为 `embed_status=failed`，文档照常可用，后续可重算。
- 均匀采样而非截断：保证覆盖全文档，避免题目只出自开头几章。
- 二期若做跨文档检索，可直接用本表已有 embedding 增量建索引，无需重构。
- 检索反而省钱：只喂相关片段，输入 token 降约 75%，同一份文档生成 2~3 次即回本 embedding 成本。

## 反转条件

当单用户资料总量达到数千切片、或需要跨资料联合检索时，重新评估引入向量库。
