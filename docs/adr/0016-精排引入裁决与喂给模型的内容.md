# 精排（两阶段检索第二阶段）：引入 ONNX Cross-Encoder，且**必须连标题一起喂**

## Status

accepted（2026-06-11）

> 上游：[ADR-0010](./0010-跨文档检索改用pgvector扩展.md)（检索双路径）、
> [ADR-0015](./0015-稀疏通道保留命中数口径并否决BM25.md)（稀疏口径与"法名不在正文里"这个结构事实）。
> 范围依据：`docs/改造计划.md` §3 第 6 项。

## Context

检索此前只有**一个阶段**（向量 ⊕ 关键词 → RRF + 标题加成），它做的是**召回**，
排序依据是"词形重合 + 向量相似"，看不见 Query 与候选之间的联合语义。

**收益上限是可以先算出来的** —— 精排只能重排已有候选，所以
`上限 = recall@pool − recall@1`。在法条域（n=135，编号类查询）上：

| | recall@1 | recall@3 | recall@5 | recall@10 | recall@20 |
| --- | --- | --- | --- | --- | --- |
| 稀疏通道（确定性基准） | 0.7111 | 0.9333 | **0.9778** | 0.9852 | **0.9926** |

> **前 5 个里几乎一定有正确答案，但排在第 1 位的不一定是它。**

剩下 0.28 的空间只能靠"把对的往前挪"来拿 —— 这就是本项的立项理由。
（先量上限再动手：若上限本身很小，266MB 的依赖就不该加。）

## Decision

### 1. 引入 `onnxruntime` + `tokenizers`，**刻意不引 torch / transformers**

权重用社区已转好的 ONNX（`Xenova/bge-reranker-base`，int8 档 **266MB**）。
引 torch 会让依赖从几十 MB 涨到数 GB，对"面试官机器上直接能跑"这条硬约束是实打实的伤害；
而本项只需要一次前向，ONNX 运行时足够。

**权重不随仓库走**（`.gitignore`），下载：`python -m app.services.rerank --fetch`。

### 2. 两阶段结构：召回 `rerank_pool`（默认 20）→ 精排 → top-k

开精排时必须**多召回**（`pool = max(k, rerank_pool)`）——池深即上限。
关精排时 `pool == k`，**行为与接入前逐字节一致**，这样"精排带来的差异"才可归因。

### 3. ⚠️ 核心结论：**必须把 `heading_path` 一起喂给模型**

这是本项最反直觉、也最值得记住的一条。初版默认只喂正文（出于"别把答案抄给模型"的测量卫生考虑），
实测**否定了这个默认值**：

| 档位（n=135） | recall@1 | recall@3 | MRR |
| --- | --- | --- | --- |
| ② 不精排（稀疏通道） | 0.7111 | 0.9333 | 0.8227 |
| ⑧ 精排·**仅正文** | **0.5630** | 0.8519 | 0.7181 |
| ⑨ 精排·**含标题** | **0.8000** | **0.9407** | **0.8753** |

**只喂正文比完全不精排还差**（−0.148）。原因与 ADR-0015 里那个结构事实**同源**：

> 法名与条号**只出现在 `heading_path` 里**（正文里没有）。
> 只喂正文时，模型分不清「教师法第七条」与「未成年人保护法第七条」，
> 于是把**语义更像**的那条排了上来 —— 一个"聪明"的模型做了错误的判断。

这条的实践含义：**精排不是"加了就涨"，喂什么进去决定符号。**
把它接上线之前必须先确认"模型能不能看到区分候选所需的那部分信息"。

⚠️ 同时必须说清另一面：**含标题的增益主要来自元数据（法名 + 条号），不是 Cross-Encoder 的语义理解。**
所以评测里两种口径**并排报**（`--rerank` 会同时跑 ⑧⑨），不合并成一个数字。
若只报 ⑨，会让人误以为这 0.09 的增益来自"模型读懂了法条"。

**拿到多少**：`0.8000 − 0.7111 = +0.0889`，占上限 `0.2815` 的约 **32%**。
即"把对的往前挪"这件事，Cross-Encoder 只解决了三分之一 —— 剩下的是排序做不到的（召回没捞全）。

### 4. 三档实现 + fail-open + 测试默认关

| `RERANK_IMPL` | 实现 | 用途 |
| --- | --- | --- |
| `onnx`（默认） | `OnnxReranker`（懒加载 + fail-open） | 生产 / 评测 |
| `fake` | `FakeReranker` | 零成本验证"重排链路接上了" |
| `off` | 不重排 | **测试套件默认** |

- **懒加载**：`__init__` 只记路径，首次 `rerank()` 才建 session ——
  否则连测试收集都会被一次 266MB 的加载拖住。
- **fail-open**：任何异常（文件损坏 / ONNX 版本不兼容 / 分词器不匹配）都**返回原顺序**
  并把原因记进 `last_error`/`status()`。精排是**增强**不是**依赖** ——
  不能让"精排坏了"升级成"检索坏了"。
- **权重缺失不自动换成 fake**：生产里"用假模型假装精排过"比"不精排"更糟，
  它会让所有精度数字失去意义。缺失由 `status()` 如实报出。
- **测试默认 `off`**：让单测依赖一次 266MB 下载是错的（慢 + 换台机器行为不同）。
  真实收益由 `eval/retrieval_eval.py --rerank` 测量，**不在单测里**。

### 5. `FakeReranker` 刻意用 Jaccard，而不是"命中比例"

"命中比例"与稀疏通道的命中数**分子相同、分母是常数** → 排序完全一致 →
把替身接上线后顺序**一点不变**，测试**测不出链路到底接上没有**。
Jaccard 多了"候选有多长"这一维，排序才会真的与粗排不同，链路测试才有意义。

## Considered Options

- **不引精排**（否决）：上限 +0.28 摆在那里且已量化，不做等于放弃。
- **引 torch + sentence-transformers**（否决）：依赖从几十 MB 涨到数 GB，
  而 bge-reranker 已由社区转好 ONNX。
- **用 API 托管重排**（否决）：破坏"离线可跑"与"零成本测试"两条现有优势，且按次计费。
- **只喂正文**（**实测否决**）：recall@1 0.5630，比不精排还差。
- **含标题但不声明其来源**（否决）：会让 0.09 的增益被误读成"模型语义能力强"。
- **权重进仓库**（否决）：266MB 二进制进 git 不可接受。
- **测试里跑真实模型**（否决）：单测不该依赖下载。
- **把 `fake` 当权重缺失时的兜底**（否决）：会让精度数字失去意义。

## Consequences

- **精排（含标题）把 recall@1 从 0.7111 提到 0.8000、MRR 从 0.8227 提到 0.8753**，
  拿到上限的约 32%。数字**跨进程可复现**（同一命令两次运行结果一致，
  遵守 ADR-0015 勘误里新立的纪律）。
- **新增一组依赖**（`onnxruntime` / `tokenizers`）与一个 266MB 的非仓库资产 ——
  这是本项目第一次引入"需要额外准备"的运行时能力；
  缓解手段是 fail-open + `status()` 如实上报 + `--fetch` 一条命令下载。
- **`retrieve()` 新增 `rerank_score` 字段**（不重排时为 `None`），
  与既有 `fusion_score` / `vector_score` / `keyword_score` / `heading_bonus` 并列，只增不删。
- **新增 16 个用例**（`tests/test_rerank.py`），其中
  `test_retrieve_在重排开启时被真的重排` 是"链路接上了"的证明 ——
  没有它，`_apply_rerank` 没接进 `retrieve()` 也测不出来。

### 已知边界（记为未决，不假装已完成）

1. **精排的评测建在稀疏通道的候选池上，不是生产融合链路的候选池。**
   原因是 `EMBEDDING_MODE=fake` 时稠密通道是字符哈希噪声，
   建在它上面的数字不可复现也不可解释（ADR-0015 勘误）。
   接入真实 embedding 后应在**生产链路**上重测。
2. **`rerank_pool=20` 没有扫过参**。池深越大上限越高、成本线性上升；
   当前值来自"法条域 recall@20 = 0.9926 已接近饱和"这一条观察，不是扫描结果。
3. **只测了 `bge-reranker-base` 一个模型**，未与其他重排器对比。
4. **延迟未测**：CPU 上 int8 每候选一次前向，本项只关心效果，没有测 P95 延迟。
   上线前需要补（`rerank_pool` 直接决定延迟）。
5. **含标题的增益与稀疏通道的 `heading_bonus` 有多少重叠，未做拆解** ——
   两者用的是同一份元数据，可能存在重复计功。

## 反转条件

1. **若 `EMBEDDING_MODE=real` 下重测，精排增益消失**，说明它此前只是在补
   fake 向量留下的缺口 —— 那时应移除本依赖（保持"零额外准备"这条优势）。
2. **若延迟实测不可接受**（`rerank_pool × 单次前向` 超出首字延迟预算），
   应下调池深或对候选做长度截断，而不是直接砍掉精排。
3. **若换用**能同时看到正文与元数据的**其他重排方案**（含把 heading
   编码进正文的训练式方案），应重跑 ⑧⑨ 两档确认"含标题"是否仍是必需。
4. **若 `document_chunks` 补上结构化元数据列**（法名 / 章 / 条，见 ADR-0015 反转条件 4），
   精排的输入构造要重新设计 —— 那时元数据可以显式拼接而非依赖 `heading_path` 字符串。
