# 官方语料命名空间隔离：`is_official` + `candidate_id` 为 NULL + 召回阶段过滤

## Status

accepted（2026-06-11）

> 上游：[ADR-0006](./0006-官方题目池与个人题库分离.md)（官方 / 个人的分离主张）、
> [ADR-0011](./0011-领域模型纠偏.md)（领域包口径）。
> 范围依据：`docs/改造计划.md` §3 第 3 项。

## Context

本项目有两类语料，可见性完全不同：

| 类型 | 内容 | 可见性 |
| --- | --- | --- |
| 官方语料 | 考纲 / 教育法条 / 评分标准（rubric） | **全员可见**，且需要被引用校验回溯 |
| 个人资料 | 用户上传的讲义 / 笔记 | **仅本人可见** |

**危险在于：这两类混在一起时不会报错。** 检索照常返回结果，只是把不该看的内容混了进去，
调用方与用户都无从察觉 —— 这正是「静默失效」的典型形态，也是本项目最想消灭的东西。

同时有一个既成事实需要处理的**术语冲突**：本仓 `scope` 历史上一直指「自然语言查询文本」
（`retrieve_by_scope(db, candidate_id, scope: str)`）；而本次引入的 `Scope` 是**过滤条件对象**。
两者同名不同义。

## Decision

### 1. `Document.is_official` 标记 + `candidate_id` 为 **NULL** 表示官方语料

| 类型 | `candidate_id` | `is_official` |
| --- | --- | --- |
| 个人资料 | 上传者 id | False |
| 官方语料 | **NULL** | True |

**为什么是 NULL 而不是哨兵 `candidate_id`**：官方语料**不属于任何考生**。
若给它塞一个哨兵 id，那么任何「按 candidate_id 查资料」的既有查询都会把官方语料一并捞出来 ——
那正是最该避免的泄漏路径。用 NULL 则 `candidate_id == x` 天然不匹配（NULL 比较为未知）。

**附带收益**：官方语料灌入后，在接入 `Scope` 之前**检索不到它**（既有查询都按 candidate_id 过滤）
—— 即 **fail-closed**。上线过程中不会意外泄漏，只有显式声明 `Scope` 才可见。

### 2. 权限过滤发生在**召回阶段**，不是检索之后

先检索后过滤会让无权文档先进入候选集：挤占 top-k、污染 RRF 排名，
而且**内容已经进了上下文**，此时过滤已失去意义。

落地位置：`kb_retrieval.load_chunks_for_scope`（内存路径）与
`retrieve_by_scope_pg` 的 WHERE（PG 路径）—— 两条路径都改，否则方言切换时语义不一致。

### 3. `Scope` 作为一等概念，三条不变量在**构造期**拦截

收敛到一个不可变对象后：加过滤维度只改一处，越权风险也只在一处审计。
三条不变量（`services/scope.py`）：

1. `namespace` 只能是三者之一 —— 拼错若被静默接受，会退化成「不按命名空间过滤」即全库可见；
2. `official` 时 `candidate_id` 必须为 None；
3. `personal` / `both` 时 `candidate_id` 必须非空 —— 留空等于个人资料全库可见。

### 4. 术语冲突的处理方式：不强行重命名，而是**分层区分 + 写进文档**

- 新入口 `retrieve(db, query: str, scope: Scope, ...)`：`query` 是文本，`scope` 是 `Scope`；
- 旧入口 `retrieve_by_scope(db, candidate_id, scope: str, ...)` 保留并委托给 `retrieve()`；
- 两个函数的文档字符串都写明这个冲突。

理由：一次改掉 4 个调用点（`kb_generate` / `kb_graph` / `run_eval` / `retrieval_eval`）是回归的主要来源。
先让新代码有干净的接口，旧调用点逐步迁移。

## Considered Options

- **建一张独立的 `official_corpus` 表**（放弃）：逻辑最清晰，但检索、去重、出题三条链路都要适配，
  与「零新表复用全链路」的既有主张冲突。
- **哨兵 `candidate_id`**（放弃）：见上文 —— 会给既有查询留下泄漏路径。
- **先检索后过滤**（放弃）：无权内容已进上下文，过滤失去意义。
- **一次性把所有调用点改成必传 `Scope`**（放弃）：回归面过大，且会掩盖真正的语义错误。
- **`personal` 的 `candidate_id` 留空时静默当作「无人」**（放弃）：那会静默返回空结果，
  把「配置错了」伪装成「没有数据」。宁可构造期抛错。

## Consequences

- **官方语料的可见性由 `Scope` 显式声明** —— 不存在"默认带上"的路径。
- **PG 的布尔字面量用 `IS TRUE` / `IS FALSE`**，不能写 `= 1`（那是 `boolean = integer`，PG 会报错；
  SQLite 才用 1/0）。下迁里的 DELETE 走 SQLite，故用 `= 1`。
- **下迁会删除官方语料**（`candidate_id` 要改回 NOT NULL，NULL 行必须先清）—— 这是数据损失，
  已在迁移 docstring 中显式说明，不静默处理。
- **新增 13 个用例**（`tests/test_namespace_scope.py`），含越权断言与「检索链路级」断言 ——
  后者防的是"有人新加一条检索路径却忘记带命名空间"。

### 已知边界（记为未决，不假装已完成）

**`Scope.subject` / `stage` / `kp_ids` 目前无法在 SQL 层生效** ——
`document_chunks` 只有 `content` / `heading_path` / `char_count` / `embedding`，没有科目 / 学段 / 考点列。
因此：

- 命名空间过滤（`namespace`）与 `doc_ids` 过滤**已实现**；
- 科目 / 学段 / 考点过滤**尚未实现**。要支持需给 `document_chunks` 补元数据列（+ 迁移），
  或在官方语料的 `heading_path` 里编码前缀再用 LIKE 过滤（便宜但耦合）。

**当前做法**：这三类字段允许传入但暂不用于过滤 —— 不做"看起来生效"的假实现。
触发实现它的条件：出现"同一问题在不同科目下答案不同"的真实需求（例如问「教学原则」时，
科目二与科目三给的口径不同）。

## 反转条件

1. 若将来官方语料需要**按用户做差异化**（例如不同学段看到不同考纲版本），
   「官方语料 candidate_id 为 NULL」这条就要重新评估 —— 那时它已经"属于某个范围"了；
2. 若科目 / 学段 / 考点过滤成为高频需求，应升级 `document_chunks` 的元数据建模，
   而不是继续用 `heading_path` 前缀硬扛；
3. 若独立表方案的成本被证明低于"复用 documents 表 + 处处过滤"，可重新评估建表。
