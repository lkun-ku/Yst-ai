# 前端框架：弃用 Taro，改用微信原生小程序

## Status

accepted（2026-05-25）—— 取代 [0004](./0004-前端框架与端策略.md)

## Context

0004 选择 Taro 4 + Vue 3 的理由是「开发者对 Vue 更熟、跨端框架生态完善」。但实测中 **Taro 的点击事件在当前环境完全失效**：`@click` 不派发，基础库 3.16.2 / glass-easel 运行时下多版本交叉验证均无法恢复；`hover-class` 正常，但只能靠 `<navigator>` 跳转兜底。

R13「资料出题」的全部交互——选择题型、加减题量、上传触发——都是**页面内配置**，navigator 无法表达。

而代码库对 Taro 只是**形式上依赖**（`.vue` SFC + Vue 响应式 + Pinia）：11 个 Taro API 在原生中均有 1:1 同名 API，NutUI 仅用到 `nut-dialog` 一处，业务逻辑无一处依赖 Taro 独占能力。

## Decision

**整体重写为微信原生小程序**（WXML / JS / WXSS），删除 Taro。

## Considered Options

- **继续 Taro + navigator 兜底**（放弃）：无法表达页面内交互，体验严重受损，核心需求做不了。
- **降级 / 更换 Taro 版本**（放弃）：已交叉验证多版本，属运行时环境变化而非某个版本的缺陷。
- **uni-app**（放弃）：同类跨端框架，有同样的运行时抽象层风险。
- **微信原生**（采用）：无框架抽象层，事件由基础库直接派发；代价是重写 9 个页面。

## Consequences

- 交互统一用 `bindtap` / `catchtap`。重写后逻辑**比 Taro 版更干净**——删除了四类 workaround：URL 编码传参、页面 redirect 重载、`process` polyfill、从 `mini.$scope` 摸原生实例。
- 零 npm 运行时依赖，不再需要「构建 npm」；自写 `modal` 组件替代 `nut-dialog`。
- 彻底放弃跨端。产品本就只承诺微信单端（0004 已如此），无额外损失。
- 单人开发下重写 9 个页面可控（页面小、逻辑简单），且可逐页人工验证。
