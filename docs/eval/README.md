# `docs/eval/` —— 基准快照与「承诺 ↔ 证据」索引

> **分工**：`backend/eval/results/` 放**原始产物**（每次跑就新增/覆盖，含运行时间与参数）；
> 本目录放**需要长期对照的基准**，以及这张**索引表**。
>
> 索引为什么必要：§6 的承诺表写的是「目标」，而数字散在十几个证据文件里 ——
> **没有这张表，"某条承诺到底达标没有"只能靠人去翻**，于是很容易一直停在"应该没问题"。

## 一条命令产出下表

```bash
cd backend && python eval/promise_report.py          # 读证据 +（fake 时）现场跑唯一性通过率
python eval/promise_report.py --live-gate            # real 模式下也现场跑（花 N 倍调用）
```

产物 `backend/eval/results/promise_report.md`：把下表的「实测」列**自动生成**，
每行带**证据文件与生成时间**（过期与否一眼可见）、**判定**、以及**来源类型**：

- **硬机制**（引用子串校验 / 闸门判定 / `max(k) < 语料规模` 这类不变量）→ 可复现、零误判；
- **LLM judge**（faithfulness / 评分一致性）→ 是「模型说的」，**低一档**。

> 把来源写进表里不是装饰：本轮修掉的三处口径错位，全都是因为"两种来源混在一张表里、
> 读数的人把它们当同等硬"。

## 三条读数的纪律（踩出来的）

1. **换了输入，旧基线就不再是基线** —— 批改依据从"纯官方语料"改成"答案库（同题型）优先 + 官方兜底"之后，
   上面那张一致性表**不能与新数字直接比较**，需要在新依据下重测（等 LLM 额度恢复）。
2. **样本变厚，结论可能翻转** —— 评分一致性的旧基线（2 题）是"达标"，扩到 7 题后变"未达标"。
   「达标」这两个字在 n=2 上没有意义。
3. **"测了"不等于"测的是那条指标"** —— 唯一性通过率这一行就是例子：有一堆 G3 证据，
   但它们测的是误杀率/拦截率，**没有一条**是"生成题目通过 G3 的比例"。指标名与测量口径必须逐字对上。
