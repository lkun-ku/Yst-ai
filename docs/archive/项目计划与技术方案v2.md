| # | 议题 | 裁决 |

| 1 | 前端技术栈 | **放弃 Taro，整体重写为微信原生小程序**（WXML/JS/WXSS），因 `@click` 在当前 glass-easel 运行时彻底失效且多版本无法恢复 |
| 2 | AI 出题商业化 | **完全免费，不做 VIP**（偏离原 S4「VIP 差异化」定位） |
| 3 | 题目质量责任 | **官方题库与个人题库分离**：分别管理、分别出题、分别判定、分别统计 |

| 6 | PDF 解析库 | **pypdf（BSD）**，商业化许可干净，质量差距用后处理清洗补。**不用 PyMuPDF——AGPL-3.0 对闭源商业化有传染性**，需购买授权 |
| 7 | 生成模式 | **双模式**：整卷走章节配额分配（主干），定点走 Top-K 检索 |
| 8 | 向量检索 | **保留 RAG**（纠正此前"一期不做"的错误判断），但用文档级内存向量检索，**不引入 Chroma** |

### 遗漏审计后补充确认的裁决（2026-03-22）

| # | 议题 | 裁决 |
| --- | --- | --- |
| A1 | **复盘维度（已核实的既有缺陷）** | `review.py:34` 遍历 `Module` 全枚举，`PERSONAL` 加入后五维雷达**会自动变六维**。修订：官方闯关闭环**排除 PERSONAL** 保持五维；个人题闯关给简化复盘（正确率 + 错题，无雷达） |
| A2 | **个人题与错题本** | 个人题错题进错题本但带 `source=doc` 标记，展示时分组/加标签，**不参与官方薄弱考点 Top3 排序** |
| A3 | **文档原文留存与版权** | 解析后**不留存原文**（仅存切片），降低版权风险；文档正文**抽样过内容安全检测**（补齐 M10"用户输入也须过检"的要求） |
| A4 | **字段补齐（已核实缺口）** | `DocumentChunk` 增 `heading_path` / `embedding` / `embed_status`；`DocTask` 增 `mode`（整卷/定点）/ `scope`（知识点范围）；需新增迁移，并修正 `DocumentChunk` 中"一期不做向量检索"的过期 docstring |
| A5 | **删除资料的级联** | `questions.doc_id` 有外键。删资料时二次确认「该资料已生成 N 题，将一并移除」，**级联删除**个人题 |
| A6 | **后台线程 DB 会话** | 后台生成线程必须开**独立 DB Session**，不得复用 FastAPI 请求作用域 Session（请求结束即关闭，并发下会崩） |
| A7 | **`wx.chooseMessageFile` UX 门槛** | 它**只能从微信聊天记录选文件**，UI 必须引导"先把文件发到聊天"；开工前用官方文档核实 `extension` 白名单与大小上限 |
| B1 | **简答计分口径** | 简答标记"待自评"，**不计入正确率分母**，计入完成度；填空题自动判 |
| B2 | **填空题答案归一化** | 去空格与标点、繁简统一、英文大小写归一、"的地得"容错——避免"填对了判错"击穿信任 |
| B3 | **个人题额度** | 个人题闯关**不消耗**每日 20 题额度（边际成本为零）；池化率统计口径**排除**个人题 |
| B4 | **术语冲突** | 补 ADR + `CONTEXT.md` 术语：资料=知识库，个人题库=题库的一种，不与"题库≠知识库"纪律冲突 |
| B5 | **多文档出卷** | ⚠️ 已实现：W-5/W-6 已落地跨文档出卷（`KbTask` + `retrieve_by_scope` 跨 `candidate_id`），原「多文档留二期」失效 |
| B6 | **每日额度口径**（原三处矛盾） | **保持 1000**（内测期），需求文档 9.1 已同步修订；测试改为引用 `FREE_DAILY_LIMIT` 常量、不再硬编码；**429 文案彻底移除 VIP 引导**，与前端 `errClassify`「不再引导 VIP」对齐 |
| B7 | **每日出题次数** | `doc_daily_gen_limit` 默认 **500**（原 2，内测期过于受限）。成本风险：按 0.15 元/次估算，重度用户单日可达数十元，上线前须按真实用量复核并考虑回落 |
| B8 | **出题数必须精确匹配** | 用户选择题量与实际生成量必须相等。曾因整卷模式把批次切了两次导致大量重复被去重丢弃；修复：段内按 `spec` 分配 + fake LLM 遵守去重 + 最多 3 轮补偿。已加 2 个回归测试精确断言题数 |
| B9 | **模考「不可回退」的含义** | 指**答题过程中不提前告知对错**，不禁止回看已答题目（保留「上一题」）。核心约束是限时 45 分钟 + 统一交卷 |
| B10 | **每日任务完成校验** | 必须**真的完成其中的题目**才能标记完成。新增 `daily_tasks.done_ids` 追踪进度，交卷时写入，`complete` 时校验，否则 400；前端未完成时禁用按钮并显示进度 |
| C1 | **工期切分** | 先交付「原生核心闭环 + AI 出题」最小可验证集，S1 / S3 在其验证通过后再做（计划中已排为阶段 6） |
| C2 | **大文件上传** | `wx.uploadFile` 设合理 timeout + 失败重试，避免 20MB 在弱网必失败 |

# 第二部分 AI 智能出题（S4 升级）技术方案

## 2.1 需求定义

用户上传文档 → 自定义**题型 / 难度 / 知识点范围 / 题目数量** → AI 生成完整试题 → 进入**个人题库** → 直接发起闯关。生成体验对标 DeepSeek 网页版（长文档、大批量、异步 + 实时进度）。

相对原始 S4 的增强：新增**知识点范围**维度（原 S4 只有"上传资料生成题目"）。

## 2.2 AI 服务选型与对比

现况：`RealLLMClient` 走 OpenAI 兼容 Chat Completions，`LLM_API_BASE`/`LLM_MODEL` 可配，stdlib `urllib` 直连（无 SDK）。**该设计天然支持换供应商，只需换 base_url + model。**

| 候选 | 中文出题质量 | 长上下文 | 结构化输出 | 成本 | 国内可达 | 结论 |
| --- | --- | --- | --- | --- | --- | --- |
| **DeepSeek**（deepseek-chat） | ⭐⭐⭐⭐⭐ | 128K | 支持 JSON mode | 极低【二手：约 $0.44/M 入、$1.32/M 出，峰谷分时】 | ✅ | **推荐主选** |
| 通义千问 qwen-plus / qwen-long | ⭐⭐⭐⭐ | 长 | 支持 | 低 | ✅ | 备选 / 兜底 |
| 智谱 GLM-4-Flash | ⭐⭐⭐⭐ | 128K | 支持 | 极低（有免费档） | ✅ | 备选 |
| 火山方舟 doubao | ⭐⭐⭐⭐ | 长 | 支持 | 极低 | ✅ | 备选 |
| OpenAI gpt-4o-mini（当前默认） | ⭐⭐⭐ | 128K | 支持 | 中 | ⚠️ | 保留为兼容默认 |

**推荐 DeepSeek 为主供应商**：① 需求明确"对标 DeepSeek 试题生成能力"，用同一模型最一致；② 中文学科知识质量强；③ 成本口径与需求分析文档 8.2 测算一致（该文档已按 DeepSeek 计价）；④ 128K 长上下文适配文档切片；⑤ OpenAI 兼容协议，改动极小。

**必须做供应商抽象**：保留 `LLMClient` 抽象基类，新增 `kind="doc_question"` 与 `LLM_PROVIDER` 配置（deepseek / qwen / openai），避免厂商锁死，为限流降级留后路。

**风险**：DeepSeek 无官方 SLA、高峰有限流 → 必须实现重试 + 备选供应商降级 + 日级告警。

### 2.2.1 Embedding 模型选型

需求分析文档 8.1 已定"国内平台用于 Embedding"，候选如下：

| 候选 | 中文效果 | 维度 | 成本 | 结论 |
| --- | --- | --- | --- | --- |
| **阿里百炼 text-embedding-v3** | ⭐⭐⭐⭐⭐ | 1024 | 极低 | **推荐** |
| 智谱 embedding-3 | ⭐⭐⭐⭐⭐ | 2048 | 低 | 备选 |
| 百度千帆 bge-large-zh | ⭐⭐⭐⭐ | 1024 | 低 | 备选 |
| OpenAI text-embedding-3-small | ⭐⭐⭐（中文偏弱） | 1536 | 中 | 不推荐 |

- 一份 200 页文档 ≈ 200K tokens，embedding 约 **0.1~0.4 元/份（一次性）**，相对生成成本可忽略
- 走与 `LLMClient` 同级的 `EmbeddingClient` 抽象，支持换供应商与失败降级

### 2.2.2 关于 LangChain / LangGraph（偏离原定的说明与建议）

原需求 8.1 定的是「LangChain / LangGraph」。**当前未引入**，我的建议是**暂不整体引入**，理由与留后路如下：

**暂不引入的理由**

1. 我们已有干净的 AI 接缝：`LLMClient`（接缝 B，Fake / Real 双实现），测试不耗额度
2. 本管线是**线性的**：解析 → 切分 → embed → 检索 → prompt → 校验 → 落库，没有多步 agent 或条件分支
3. 主要用到的能力均可轻量自给：`pypdf` + `python-docx` 解析约 50 行；1500/200 滑窗切分约 20 行；JSON 修复约 10 行
4. 引入全套 LangChain 会增加较大依赖树、版本 churn 与一层抽象，对单人开发的长期维护成本不友好

**建议的折中**

- 若想保留 LangChain 生态红利，可**只装 `langchain-text-splitters`**（轻量、无全套依赖），用其 `RecursiveCharacterTextSplitter` 做切分
- 保留引入 LangGraph 的可能：**当出现多步编排需求时**（主观题批改的多轮追问、模考后的分支建议），LangGraph 才真正发挥价值，届时引入属自然演进

> **✅ 已裁决（2026-03-22）：不引入 LangChain / LangGraph。**（保留当时结论以存档）
>
> **🔄 结论已更新（2026-03-29，见 ADR-0009；ADR-0008 已标 superseded）**：知识库出题引入**质量闭环**（检索相关性评分 → 改写重检索、生成自检 → 重生成）后，编排已包含条件分支与多轮流转，上述「多步编排需求」这一反转条件**已被满足**。经三路线代码级对比实验（fake 离线 + 真实 LLM 双验证），**采纳路线③ LangGraph 为生产默认**（`route="graph"`），手写路线② 以 `route="handwritten"` 保留为回退与评测对照。
>
> 精确口径：**仍不引入** LangChain 全套及其检索层封装（`PGVector` / `EnsembleRetriever`）；单文档出题管线依旧不依赖任何编排框架，本段对**单文档场景**的判断仍然有效。依赖仅新增 `langgraph==1.2.11` + `langchain-core==1.6.2`。

## 2.3 文档解析、切分与向量检索

> **方案修正说明**：上一版写"一期不做向量检索"，这是基于成本与复杂度的单方面判断，**未经裁决且判断有误**。原需求 8.1 明确要求「MySQL + 向量库（Chroma 或同类）用于 RAG 知识库」，S4 本身就叫「RAG 知识库」，7.4 权属条款亦以"用户通过 RAG 上传的资料"表述。RAG 是本需求的题中应有之义，现补回。

### 为什么必须有检索（四条理由）

1. **PDF 没有可靠标题结构**：`pypdf` 抽出的是扁平文本流，上一版依赖的"章节树 / `heading_path`"在 PDF 上大概率失效——这是上一版设计真实存在的漏洞。
2. **知识点范围是自由文本**：如"教师的权利""德育原则"，需要语义匹配，字面关键词召回率低。
3. **喂无关内容会损害质量**：上下文中混入无关片段会干扰模型，并诱发幻觉。
4. **检索反而降成本**：输入 token 可降约 75%，测算见 2.7。

### 解析（新增依赖 `pypdf`、`python-docx`；TXT/MD 直接解码）

| 格式 | 方案 | 边界处理 |
| --- | --- | --- |
| PDF | `pypdf` 逐页抽取文字层 | **无文字层检测**：抽取文本量 < 阈值 → 提示"扫描版 PDF 无文字层，请提供可复制文本的版本"。**一期不做 OCR** |
| DOCX | `python-docx` 遍历 paragraphs + tables | 表格转为行文本 |
| TXT / MD | 直接解码（utf-8 → gbk 回退） | MD 保留标题结构用于章节识别 |
| 上限 | `DOC_MAX_MB=20`、200 页 / 30 万字截断 | 防内存与 token 爆炸 |

#### PDF 解析库选型（含许可风险提示）

| 库 | 许可 | 抽取质量 | 安装稳定性 | 结论 |
| --- | --- | --- | --- | --- |
| **pypdf** | **BSD** ✅ | 中：中文 PDF 易断行（`教\n师`）、页眉页脚混入、双栏乱序 | 纯 Python，无编译依赖，最稳 | **推荐主选** |
| PyMuPDF (fitz) | **AGPL-3.0** ⚠️ | 高：版面块排序、双栏重排、图片页检测准、快约 10x | 有预编译 wheel，一般 OK | 质量最优但**许可有风险** |
| pdfplumber | MIT | 高（表格强） | 依赖 pdfminer.six，较慢 | 备选（表格密集场景） |

> **⚠️ 关键提醒：PyMuPDF 是 AGPL-3.0**。本项目未来要商业化，AGPL 对闭源分发有传染性，需购买商业授权才能合规使用。
> **✅ 已裁决（2026-03-22）：使用 pypdf（BSD）。** 质量差距用后处理清洗补：按空行合并断行、按页眉页脚重复模式剔除、过滤短行与页码行。

### 两级切分

1. **结构切分**：按 MD 标题 / DOCX 标题样式 / 空行 / 短行识别章节边界，记录 `heading_path`（如 `第三章 > 3.2 > 3.2.1`）。**PDF 识别不出结构时 `heading_path` 为空，此情形必须靠向量检索兜底。**
2. **语义切分**：结构块内滑窗，`DOC_CHUNK_SIZE=1500 字`、`OVERLAP=200 字`

每个 chunk 落 `document_chunks`：`doc_id / seq / heading_path / char_count / text / embedding / embed_status`。

### Embedding 与存储

- 上传解析完成后**异步**为每个 chunk 生成 embedding，存 `document_chunks.embedding`（BLOB）
- **原判断（单文档场景，仍成立）**：检索范围是**单个文档**时不需要向量数据库：
  - 单文档上限 200 页 ≈ 300K 字 / 1500 字 ≈ **约 200 个 chunk**
  - 200 × 1024 维余弦相似度，纯 Python 即为毫秒级；加 `numpy` 更稳
  - 因此 Chroma 带来的独立持久化目录、较重依赖树与部署复杂度，**在文档级规模下不划算**
- **🔄 已升级（2026-03-29，见 ADR-0010；ADR-0007 已标 superseded）**：跨文档出题（`kb_retrieval.retrieve_by_scope`）落地后，检索范围从「单文档约 200 chunk」变为该考生**全部资料切片**（跨文档累计数千～数万），ADR-0007 的反转条件「需要跨资料联合检索」被触发：
  - **dev / SQLite**：仍为内存 numpy 混合检索（本段原方案不变，无需 PG）
  - **生产 PostgreSQL**：启用 **pgvector 扩展** —— 新增 `embedding_vec VECTOR(1024)` 列 + HNSW 索引（`m=16, ef_construction=64, vector_cosine_ops`），检索改为 SQL 余弦；`retrieve_by_scope` **按方言自动分发**，两条路径返回结构一致
  - **仍不引入 Chroma 等独立向量数据库服务**：pgvector 是 PostgreSQL 扩展而非独立部署，无双写同步与权限重建成本（ADR-0007 对独立向量库的判断依然成立）
  - 已验证：腾讯云 TencentDB PostgreSQL 18.x + pgvector **0.8.2** 端到端通过

### 混合检索（向量 + 关键词）

单一向量检索有盲区：用户查"第三章"这类字面表述，向量相似度反而不准。采用混合召回：

| 通道 | 适用 | 实现 |
| --- | --- | --- |
| 向量检索 | 语义化知识点（"教师的权利"） | `cosine(embed(query), embed(chunk))` 取 Top-K |
| 关键词 / 标题检索 | 字面章节（"第三章"）、专有名词 | `heading_path` 前缀匹配 + chunk 文本包含匹配 |

- 两路召回合并去重后按分数排序，取 Top-K（默认 `K=8`，约 12K 字）
- 用户在出题页**勾选章节**时，先用 `heading_path` 硬过滤，再在子集内做向量排序
- 未指定范围 → 全文档向量检索，或按上下文预算走均匀抽样

### 降级策略（检索不可阻塞上传）

embedding 服务不可用或超时时，**不允许导致上传失败**：

```
向量检索 → 关键词/标题检索 → 全量均匀采样
```

- 上传时 embedding 失败：文档照常可用，置 `embed_status=failed`，生成时自动走关键词降级，并在结果页轻提示"本次为关键词匹配，题目覆盖可能不全"
- 提供后台任务对 `embed_status=failed` 的文档重算

### 上下文预算与可追溯

- 选中 chunks 总长超预算（如 30K 字符）时，**均匀抽样（保序）而非简单截断**——简单截断会导致题目只覆盖文档前三章
- 片段带 `[资料片段 n]` 标记，要求模型在题目里回标 `source_chunk` → **可追溯、可校验、可溯源到原文**

## 2.4 提示词工程设计

**System（固定）**：角色设定 + 五条硬约束 —— ① 只能依据给定资料，**禁止引入外部知识**；② 资料未涉及的内容不得生成；③ 严格输出 JSON；④ 每题回标 `source_chunk`；⑤ 内容合规。

**User（按题型分模板，与分批生成一一对应）**：

| 题型 | Prompt 要点 | 输出约束 |
| --- | --- | --- |
| single / multiple | 4 选项、干扰项须合理且同质、答案唯一 / 多答案 | `options[{key,text}]` + `answer[]` 必须命中选项键 |
| judge | 题干为陈述句，不得含"以下说法是否正确"之类套话 | 答案二值（正确 / 错误） |
| blank | 题干含 `___`，答案给出**可接受变体列表**（同义、别称、简写） | `answer[]` 为文本列表 |
| short | 参考答案 + **评分要点**（3~5 条） | 不自动判分，标记待自评 |

**关键设计**：

- **防幻觉**：显式指令"若资料不足以支撑所要求的题量，宁可少出也不要编造"，并返回实际生成数
- **难度具象化**：`easy` = 原文复现；`medium` = 需归纳；`hard` = 跨段落综合 / 推理——避免模型对"难度"自由发挥
- **去重**：prompt 末尾附已生成题干列表（归一化后、截断），显式禁止重复
- **温度**：出题 **0.3**（稳定可复现），复盘段落 0.7
- **JSON 可靠性三层保障**：`response_format=json_object` → 本地 JSON 修复（首个 `{` 到末个 `}`）→ 结构化校验失败则重试（最多 2 次，仍失败即弃该批）

## 2.5 题库生成流程

```
上传(wx.chooseMessageFile) → wx.uploadFile → POST /api/documents
  → 解析 + 两级切分 → documents + document_chunks → 返回章节树
  → 用户配置 spec[{type,count}] + difficulty + scope(章节/关键词) + focus
  → POST /api/documents/{id}/generate → 建 doc_tasks(pending) → 返回 task_id
  → 后台线程：按 scope 选 chunks → 按题型逐批生成（每批 5~10 题）
      → LLM(重试) → 按题型专属校验(不通过即弃) → 内容安全(不过即弃)
      → stem 归一化去重 → 落 questions → 更新 doc_tasks.done/total
  → 前端轮询 GET /api/tasks/{id}(1.5s，onUnload 清定时器)
  → 完成 → 开始闯关（个人题库）
```

- **批次策略**：每批 5~10 题。太多 → 模型不遵守配比且质量下降；太少 → 成本上升
- **失败隔离**：单批失败不影响其他批；全部失败 → `status=failed` + error + 重试入口
- **幂等**：`spec` 归一化后算 hash，同文档同配置重复提交直接复用已有结果，**避免重复计费**

### 两种生成模式（关键设计修正）

> **修正说明**：向量检索 Top-K 是为「按知识点出几道题」优化的。但"帮我出一份试题"是**整卷**需求，Top-K 会把题目集中到语义密度最高的章节，导致**30 题全扎堆在第 2 章**。必须区分两种模式：

> **✅ 已裁决（2026-03-22）：双模式都做，整卷（章节配额）为主干。**定点模式作为补充，供用户针对薄弱环节精准练题。

| 模式 | 目标 | 检索策略 | 分批维度 |
| --- | --- | --- | --- |
| **整卷模式** | 覆盖全文档、分布均匀 | **章节配额分配** | 章节 × 题型 |
| 定点模式 | 精准命中指定范围 | Top-K 语义/关键词召回 | 仅按题型 |

**整卷模式的配额分配算法**：

```
1. 按 heading_path 或结构边界把文档分为 N 段
2. 按段长比例分配题量（30 题 / 5 章 → 每章 6 题）
3. 每段独立检索 + 独立生成
4. 配额补偿：某段生成不足（资料支撑不够/被校验丢弃）时，
   按剩余段长度比例补偿，保证总题数达标
```

### 成卷组装（决定"一份试卷"vs"一堆题"的观感）

生成落库后，在组装层统一处理：

- **题号连续编排**：跨批次重排为 1..N
- **分题型分区**：一、单选题 / 二、多选题 / 三、判断题 …
- **试卷 / 答案卷分离**：题目区不含答案，答案与解析单独成区，支持"只看题"自测
- AIGC 标识落在这两层（题目卡片 + 解析区），满足合规

### 跨批去重

分批生成最容易出的质量问题是**重复题**。必须做跨批 stem 归一化去重（去标点、空白、繁简/大小写归一），否则一份 30 题的卷子出现多道近义题，观感很差。

## 2.6 与现有系统的集成架构（双题库分离）

本轮裁决③的架构落地，也是 **R1 致命风险的架构级缓解**：

| 维度 | 官方题库 | 个人题库 |
| --- | --- | --- |
| 标识 | `source=POOL` + `owner_candidate_id IS NULL` | `source=DOC` + `owner_candidate_id=本人` + `doc_id` |
| 模块 | 官方五维 | `Module.PERSONAL`（独立维度） |
| 质量责任 | 结构化校验 + 人工抽检（R1） | **用户自负，无审校** |
| 出题入口 | `quest` 页按模块 | `docs` → `generate` 按资料 |
| 判定 | 单/多选集合比较 | 按题型分派（填空文本匹配 / 判断二值 / 简答不判分） |
| 掌握度 | 五维雷达 | `PERSONAL` 独立维度，**不污染五维** |
| 成本计量 | 计入池化率（≥95% 硬约束） | **单独计量，不计入池化率** |

**核心价值**：即便个人库出现错误题目，也被**永久隔离在个人库**，永远不会流入官方池、不会影响其他用户——这正是对"AI 生成错误题目误导考生"这一致命风险的结构性防线，比"人工抽检"更适配"用户自主上传"场景。

**改动边界（严格遵守）**：

- 不改 `api.ts` 去重锁与 `toastApiError` 语义
- `start_session` 默认分支仍只取官方池，个人库走新增 `doc_id` 入参分支
- `validate_question_payload` 按 `type` 分派重构时，**官方池路径行为必须逐字节不变**

## 2.7 性能与成本控制

**⚠️ 这是免费策略下最大的风险点。** 文档出题属实时生成，直接冲击 ADR-0002 的预算硬约束。

### 单次成本估算【估算，汇率 7.2，DeepSeek 计价为【二手】】

| 项 | 量级 | 成本 |
| --- | --- | --- |
| 每批输入（文档片段 + prompt） | ~6K tokens | ≈ 0.019 元 |
| 每批输出（5~8 题） | ~2K tokens | ≈ 0.019 元 |
| **每批合计** | 5~8 题 | **≈ 0.038 元** |
| **一次典型生成（20 题 / 4 批）** | — | **≈ 0.15 元** |
| 文档 embedding（一次性，可反复复用） | 200 页 ≈ 200K tokens | ≈ 0.1~0.4 元/份 |

> **关键点：检索不花钱，反而省钱。** 一份文档只 embed 一次、可反复出题；启用检索后每批只喂相关片段（约 7.5K 字）而非全量（30K 字），**输入 token 降约 75%**。同一份文档生成 2~3 次即回本 embedding 成本。这推翻了"向量检索贵所以要砍"的直觉。

**风险测算**：若 500 DAU 中 10% 使用、每人每日 1 次 20 题 → `50 × 0.15 ≈ 7.5 元/天 ≈ 225 元/月`。叠加服务器 100~250 元，**逼近甚至突破 300 元/月预算上限**。

### 必须落地的六条硬约束

1. `DOC_DAILY_GEN_LIMIT` 每日生成次数上限（建议 **2 次**，对齐 ADR-0002「每人每日实时生成上限 3 次」精神）
2. `DOC_MAX_Q_PER_TASK` 单次题量上限（建议 **30 题**）
3. **输入长度上限**：只喂选中章节，且 ≤ 30K 字符（成本主要来自输入）
4. **结果复用**：生成的题进个人题库后可**反复闯关，不重复计费**——一次生成、多次使用，是摊薄成本的关键
5. **幂等缓存**：同文档同 `spec` hash 复用结果，防重复提交烧钱
6. **日级告警 + 自动降级**：复用 ADR-0002 第 5 条，超阈值提示"今日生成额度已用尽"

### 性能

- 解析：同步但受 20MB / 200 页上限保护
- 生成：后台线程串行批，20 题 ≈ 1~2 分钟 → **必须靠进度反馈兜住体感**
- 并发：线程池限流（最多 3 个并发任务），避免打爆 LLM 限流
- 任务恢复：进程启动时把 stale `running` 任务标记 `failed`（后台线程在单进程重启时会丢）
- 前端：`setData` 只传增量，题目流逐条追加

### 与 DeepSeek 的差距（诚实说明）

它在 OCR、多模态、超长上下文工程优化上有专门团队，我们一期不做 OCR、不做跨文档全库检索。我们的差异化在**垂直场景**：生成结果直接进个人题库并打通闯关 / 判定 / 复盘 / 错题本闭环，这是通用 AI 网页版给不了的。

## 2.8 与企业后台 RAG 问答机器人的异同

"文档出题"与企业知识库问答机器人**共享 RAG 骨架**（解析 → 切分 → embedding → 检索 → 拼上下文 → 生成），但**三个关键环节的取向相反**，因此不能照搬架构：

| 维度 | 企业 RAG 问答 | 文档出题 | 影响 |
| --- | --- | --- | --- |
| 检索范围 | **全库跨文档**（数千文档 / 百万 chunk） | 单文档内 ≈ 200 chunk；**跨文档出题已落地**后为该考生全部切片 | 单文档场景内存暴力余弦即可（→ 不引 Chroma 的依据）；**跨文档场景已改用 pgvector 扩展 + HNSW**，见 ADR-0010 |
| 检索目标 | 找**最相关**的几段（精准优先） | 找**覆盖均匀**的段落（整卷场景） | 前者 Top-K 即正确；后者 Top-K 会扎堆 → **必须章节配额** |
| 输出形态 | 自然语言段落（容错高） | **结构化 JSON**（容错为零） | 后者必须额外投入格式三层防护 + 题型校验 + 分批 |
| 输出长度 | 短（几百字） | 长（整卷 30 题） | 后者必须分批，否则长输出截断 |
| 正确性判定 | 主观，靠引用溯源让用户自查 | **可机器校验**（答案命中选项、解析非空） | 后者能自动丢弃坏题，前者不能 |
| 是否多轮 | 是（需对话上下文） | 否（一次性任务） | 后者无需会话状态管理 |

**可借鉴的成熟实践**：引用溯源（`source_chunk`）、幻觉抑制（"只依据资料、资料不足宁可少出"）、语义完整性切分、混合检索（向量 + 关键词/BM25）。

**不可照搬的部分**：检索策略（覆盖 vs 精准）、输出层（结构化校验 vs 自然语言）、以及"是否需要向量数据库"这一基础设施判断。

更准确地说，本需求最接近的同类任务是 **「长文档 → 结构化数据集生成」**（如合同关键条款抽取、论文生成综述），其共性是：**覆盖均匀 + 结构化输出 + 结果可机器校验**。

## 3.1 S1 连胜 + 补签卡

> 原文：`S1 | 连胜 + 补签卡 | 强留存机制；严禁「分享得补签」（诱导分享红线）`
> 现状：❌ 未实现（backend 无 streak 相关表或字段）

### 连胜定义

- 连续**完成每日任务**的自然日数。完成判定复用现有 M5 逻辑（`daily_tasks.completed = true`），不另立标准
- 时区：服务端固定 `Asia/Shanghai` 本地日期，与 `DailyTask.task_date` 口径严格一致

### 数据模型（新增两张表）

```
streaks
  candidate_id   PK FK candidates.id
  current        int   当前连胜
  max            int   历史最高
  last_date      str   最近完成日 YYYY-MM-DD
  cards          int   补签卡余量（上限 3）
  total_days     int   累计达标天数
  updated_at

streak_makeups                        # 补签流水，保证幂等
  id
  candidate_id
  missed_date    str   被补的日期
  used_at
  UNIQUE(candidate_id, missed_date)
```

### 连胜推进算法（在完成每日任务的事务内同步执行）

```
today = local_date()
if last_date == today:            # 已完成，幂等，不动
    pass
elif last_date == today - 1:      # 连续
    current += 1
else:                             # 断连
    current = 1                   # 先断，等用户主动补签后恢复
max = max(max, current)
last_date = today
```

### 补签卡

**获取途径（三条，全部为学习行为激励，绝不涉及分享/邀请/广告）**：

| 触发 | 发放 | 上限 |
| --- | --- | --- |
| 连胜达到 3 / 7 / 14 天 | 各 1 张 | — |
| 单局正确率 ≥ 80% | 1 张 | 每周 1 张 |
| 清空某考点全部错题 | 1 张 | 每月 1 张 |

- 上限 `cards ≤ 3`，防囤积、防无限续命削弱连胜意义
- **仅可补最近 1 个漏掉的自然日**；补签后 `current = 断连前值 + 1`，写 `streak_makeups` 保证同一天不可重复补
- **红线检查**：接口层不提供任何"分享 / 邀请 / 看广告"发放入口，`cards` 只允许由服务端学习事件写入

### 接口

- `GET /api/streak` → `{ current, max, cards, today_done, can_makeup, makeup_date }`
- `POST /api/streak/makeup` `{ date }` → 校验余量 + 幂等 + 恢复连胜

### 前端（原生）

- 首页新增连胜卡片：火焰数字 + 近 7 日点阵（已达标高亮）
- 补签入口在卡片内，`can_makeup = true` 时点亮
- 补签成功给轻动效（数字跳动）

### 容错

连胜推进失败**不得阻塞**每日任务完成 → 放在事务外，用 try/except 兜底并记日志。

## 3.2 S2 分段排行榜

> 原文：`S2 | 分段排行榜 | 20 人一组、按水平分组，让普通用户也能上榜`
> 现状：❌ 未实现

### 为什么不做全局榜

全局榜 = 头部用户固化，新手永远垫底，与"强留存"目标相反；且 3.1 用户画像明确"对错误的容忍度低"，垫底体验会直接损害信任。

### 分组策略（确定性分桶，不用随机）

- **主维度**：近 20 局平均正确率分档
  - `L1 <50%` / `L2 50–65%` / `L3 65–80%` / `L4 ≥80%`
- **副维度**：考期（`Candidate.exam_date`），保证同期备考可比
- 桶 key = `f"{level}:{exam_date}"`，同桶内排序取 Top 20

### 榜单指标（关键设计）

**不用累计题量**（鼓励无意义刷题、富人愈富）。采用**本周学习分**：

```
score = 完成局数 × 10 + 平均正确率(%) × 0.5 + 连胜天数 × 2
```

只统计 `status = SUBMITTED` 且在本周内的局。

### 数据

- 一期不建新表，直接基于 `sessions`（`submitted_at`、`result_json`）+ `streaks` 聚合
- 内测 200 人量级可直接 SQL；DAU 上来后加 `weekly_stats` 物化表或定时快照

### 接口

`GET /api/leaderboard?scope=week`
→ `{ bucket, my_rank, my_score, total_in_bucket, list:[{ rank, nickname_masked, score, is_me }] }`

### 隐私与合规

- 昵称脱敏（`张**`），不返回 unionid / openid
- `settings` 页提供「不参与排行榜」开关；关闭后不出现在任何榜，且不参与分桶基数
- 默认开启，但首次进入需做一次说明

### 空榜兜底

桶内人数 < 5 时：不显示排名，改显示"你在本周超过了 X% 的同水平考生"（用全库分位计算），避免出现"第 1/1 名"的空虚感。

### 反作弊

只统计真实提交局；`result_json` 幂等缓存防重复计分；提交频率异常（如 1 分钟内 > 3 局）不计分。

## 3.3 S3 模考

> 原文：`S3 | 模考 | 限时、不可回退、统一交卷`
> 现状：❌ 未实现

### 与闯关局的差异（明确边界）

| | 闯关（normal） | 模考（mock） |
| --- | --- | --- |
| 题量 | 10 | 30（可按真实卷折算） |
| 回退 | 可 | **不可** |
| 即时判定 | 有 | **无**（答题中不显示对错） |
| 计时 | 无 | **限时 45 分钟** |
| 解析 | 即时展开 | 交卷后统一 |
| 题目构成 | 单模块 / 考点 | **按官方权重 15/15/10/12/48 抽题** |

### 数据模型（复用 sessions，不建第二套）

`sessions` 新增字段：

- `mode`（`normal` / `mock`）
- `duration_sec`（默认 2700）
- `deadline_at`（服务端绝对时间）
- `timeout`（是否超时交卷）

这样 `_judge` 判定、`review` 复盘、错题本、历史回看**全部零改动复用**。

### 限时（防客户端改时间）

- `POST /api/sessions/start { mode:"mock" }` 响应返回 `server_now` + `deadline_at`
- 前端用 `offset = server_now - Date.now()` 校正本地时钟，倒计时 = `deadline_at - (Date.now() + offset)`
- 归零前端**自动提交**
- 服务端提交时校验 `now <= deadline_at + 30s 宽限`；超时则按已答部分判分并置 `timeout = true`
- 后台切前台用 `onShow` 重新校正倒计时，防挂后台偷时间

### 不可回退

- 前端只渲染当前题，无「上一题」按钮
- 答案本地累积在 `answers` 数组
- 物理返回键用 `wx.enableAlertBeforeUnload` 二次确认（原生可直接调，无需 Taro 的 `$scope` hack）

### 统一交卷

答完 / 超时 / 主动交卷 → 复用 `POST /api/sessions/submit`，判定复用 `_judge`（含后续题型分派）。

### 模考报告

复用 `review`，额外增加：用时、剩余时间、按卷面 58 分折算的**估分**。折算口径须在报告里标注为估算，避免误导。

### 接口变更

- `POST /api/sessions/start` 增加可选 `mode`，返回 `server_now` / `deadline_at`
- `GET /api/sessions/{id}` 返回 `mode` / `deadline_at`
- **不改动 `submit` 契约**
