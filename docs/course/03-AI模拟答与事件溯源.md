## 1. 一个反直觉的选择

要实现一个「AI 面试官追问」的对话功能，你可能的第一反应是：

```python
class ChatSession(Base):
    current_question_index: int      # 当前是第几题
    probes_used: int                 # 这一题已经追问几次
    current_question: str            # 当前题目内容
    key_points: str                  # 当前题的评分要点
    is_graded: bool                  # 当前题是否已出分
```

**本项目的代码里，这些字段一个都没有。** 它只存「发生过什么」：

```414:431:backend/app/models.py
class ChatTurn(Base):

    role: Mapped[str] = mapped_column(String(8))  # ai | user
    turn_type: Mapped[str] = mapped_column(String(16))  # opening | ask | probe | feedback | user
    content: Mapped[str] = mapped_column(Text)
    question_id: Mapped[int | None] = mapped_column(ForeignKey("questions.id"), nullable=True)
    score: Mapped[int | None] = mapped_column(Integer, nullable=True)  # feedback 轮 0-100
    points_hit: Mapped[str | None] = mapped_column(Text, nullable=True)  # JSON 数组
    points_missed: Mapped[str | None] = mapped_column(Text, nullable=True)
    points_wrong: Mapped[str | None] = mapped_column(Text, nullable=True)
    suggestion: Mapped[str | None] = mapped_column(Text, nullable=True)  # 改进建议
    created_at: Mapped[datetime] = mapped_column(DateTime(timezone=True), default=_utcnow)
```

**没有 `current_question_index`，也没有 `probes_used`。**

**【原理】Event Sourcing（事件溯源）**：不存储「当前状态」，只存储「发生过的事件」，
状态在需要时由事件流**计算**出来。

## 2. 投影：状态是算出来的

```190:213:backend/app/routers/chat.py
def _current_question(db: ORMSession, s: ChatSession) -> tuple[ChatTurn, list, int]:
    """定位当前未终评的题：最后一轮 ask 与已追问次数。"""
    turns = (
        db.query(ChatTurn)
        .filter(ChatTurn.session_id == s.id)
        .order_by(ChatTurn.seq)
        .all()
    )
    last_ask = next((t for t in reversed(turns) if t.turn_type == "ask"), None)
    if last_ask is None:
        raise HTTPException(409, "当前没有待回答的问题")
    # #33 补充轮次 = 该 ask 之后的 probe + hint 轮数（提示也占用上限，
    # 否则用户反复离题会永远收提示、拿不到分、没有出口）
    idx = turns.index(last_ask)
    probes = sum(1 for t in turns[idx + 1 :] if t.turn_type in ("probe", "hint"))
    # 终评已出且未被新一轮 ask 覆盖 → 场次已收尾
    if any(t.turn_type == "feedback" for t in turns[idx + 1 :]):
        raise HTTPException(409, "本题已出分，请继续下一题或结束训练")
    # #32：要点复用 ask turn 的 points_hit 列存储（纯 LLM 生成路线不走 ChatPack 缓存，零迁移）
    key_points = json.loads(last_ask.points_hit) if last_ask.points_hit else []
    if not key_points:
        # 纯生成改造前的旧会话无要点：明确 409 让前端清掉本场重开，不要 500
        raise HTTPException(409, "本场为旧版对话，请重新开始训练")
    return last_ask, key_points, probes
```

**三行推导逻辑**：

| 要算的状态 | 怎么从事件流算 |
|---|---|
| 当前题目 | 倒着找最后一个 `ask` |
| 已追问次数 | 数它后面有几个 `probe` / `hint` |
| 是否已出分 | 它后面有没有 `feedback` |

```
事件流:  [opening, ask, user, probe, user, feedback, ask, user]
                                          ↑              ↑
                                     上一题已出分    当前题（最后一个 ask）
                                                     后面 0 个 probe → 未追问
```

**【原理】这就是投影（Projection）**：把事件流「折叠」成一个状态。

### Event Sourcing 的三大红利

| 红利 | 在本项目里怎么体现 |
|---|---|
| **状态不会与流水不一致** | 没有 `probes_used` 字段，就不可能存在「字段说是 2，流水里只有 1 个 probe」的矛盾 |
| **完整可重放** | `GET /api/chat/session/{id}` 把所有 turn 吐给前端，切后台回来现场完全恢复 |
| **可自愈** | 见第 4 节 —— 这是最有价值的一条 |

### 一个实用的「省字段」技巧

```python
# #32：要点复用 ask turn 的 points_hit 列存储（纯 LLM 生成路线不走 ChatPack 缓存，零迁移）
key_points = json.loads(last_ask.points_hit) if last_ask.points_hit else []
```

出题时把「评分要点」塞进 `ask` 回合的 `points_hit` 列（本来那是给「命中要点」用的），
评分时再读出来。**本质是复用列来存题目附带数据，避免加表加字段。**

⚠️ 这是**可接受的权衡而非优雅设计** —— 注释里明确写了「零迁移」这个动机。
代价是语义复用（同一列在不同 `turn_type` 下含义不同），后续接手的人容易误读。
**如果重来一次，加一个 `key_points` 列会更清晰。**

## 3. 三态状态机

评分 prompt 让模型返回三选一的判断：

```240:276:backend/app/services/llm_client.py
        if req.kind == "chat_grade":

                f'{persona_style}。\n'
                f'面试问题：{ctx.get("open_question", "")}\n'
```

注意 prompt 里 **明确写了每个状态的进入条件，以及「已达上限必须 final」**。
这是把状态机的转移规则**写进了提示词**。

完整的转移图：

```
用户回答
   │
   ├─ 完全跑题 (off_topic) ──→ 给 hint 提示，补充轮次 +1
   │
   ├─ 空泛/没踩到要点 (need_probe) ──→ 追问一句，补充轮次 +1
   │
   └─ 答到点上了 (final) ──→ 打分 + 记录命中/遗漏要点
   
   ⚠️ 补充轮次 ≥ MAX_PROBES(2) → 强制走 final，无论如何给分
```

### 那个「强制出口」是整套设计的灵魂

```351:359:backend/app/routers/chat.py
    # 终评（need_probe / off_topic 但已达补充轮次上限也强制终评——用户永远有出口）
    hit = payload.get("hit") or []
    ...
    if verdict == "off_topic":
        # LLM 仍判离题但已达上限：按零命中终评，不给用户无限循环的空洞
        hit, missed = [], list(key_points)
        payload["feedback"] = payload.get("feedback") or "几轮下来没有围绕这道题作答，这题先记个低分，我们换下一题。"
```

**【原理】任何交互式 AI 产品都必须有「强制出口」。**

AI 对话最常见的死循环：用户一直答非所问 → AI 一直追问 → 永远没有结果 → 用户觉得产品在耍他。

本项目的处理：

1. `MAX_PROBES = 2` 硬性截断
2. **hint 和 probe 共享同一个上限**（注释：否则用户反复离题会永远收提示、拿不到分、没有出口）
3. 达到上限后即使模型仍判 `off_topic`，也按「零命中」给低分并进入下一题

**注意第 2 点**：如果 hint 和 probe 各算一个上限，用户可以无限吃 hint。
共享计数是防止「用提示绕过追问上限」。

## 4. fail-close 与自愈

### 评分失败绝不静默给分

```326:329:backend/app/routers/chat.py
    payload = res.payload if res else None
    if not payload:
        # 显式失败：不落任何 turn（本题状态不变，可重试），绝不静默给分
        raise HTTPException(503, "AI 评分暂时不可用，请稍后重试")
```

**【原理】fail-open vs fail-close**

| 类型 | 含义 | 本项目里的例子 |
|---|---|---|
| **fail-close** | 失败就报错，绝不糊弄过去 | 评分、内容安全 |
| **fail-open** | 失败就降级，不阻塞流程 | embedding、自检、检索 |

**判断标准：这个失败如果「静默通过」，用户会不会被误导？**

- 评分被误导（拿到一个假的 60 分）→ **fail-close**
- 向量化失败（降级成关键词检索，效果差些但结果仍真实）→ **fail-open**

注意注释里的关键一句：**「不落任何 turn（本题状态不变，可重试）」** ——
因为状态是从事件流推导的，只要不追加事件，状态就完好无损，用户重试即可。

**如果用状态字段写，这里就要考虑「失败时该回滚哪些字段」—— 复杂且易错。**

### 自愈：Event Sourcing 的杀手级应用

终评成功之后要出下一题，但出题可能失败（503）。如果让整个请求失败，
用户就卡死了：分已打完，但没有下一题，再点什么都没用。

```384:389:backend/app/routers/chat.py
    try:
        payload2 = _gen_question(llm, s.difficulty, s.persona, avoid=asked)
        next_ask = _ask_turn(db, s, payload2)
    except HTTPException:
        next_failed = True
        db.rollback()
```

处理方式是：**终评照常落库返回，出题失败只标记 `next_failed: true`**。
用户下一条消息进来时触发自愈：

```273:303:backend/app/routers/chat.py
    # #36 自愈：上一题已终评但下一题出题失败（历史 503 遗留的卡死态）→ 先补出题。
    # 用户这条消息将作为新题的回答，重发即恢复，无需任何特殊操作。
    turns = (
        db.query(ChatTurn)
        .filter(ChatTurn.session_id == s.id)
        .order_by(ChatTurn.seq)
        .all()
    )
    last_ask = next((t for t in reversed(turns) if t.turn_type == "ask"), None)
    if last_ask is not None:
        idx = turns.index(last_ask)
        if any(t.turn_type == "feedback" for t in turns[idx + 1 :]):
            asked = [t.content for t in turns if t.turn_type == "ask"]
            payload_heal = _gen_question(llm, s.difficulty, s.persona, avoid=asked)
            _ask_turn(db, s, payload_heal)
            ...
    elif not any(t.turn_type == "ask" for t in turns):
        # active 场却没有任何 ask（异常残留）→ 同样补题
        payload_heal = _gen_question(llm, s.difficulty, s.persona, avoid=[])
        _ask_turn(db, s, payload_heal)
        ...
```

**为什么这段代码能这么短？**

因为「系统处于异常状态」这个判断，被表达成了**事件流的一个特征**：

```
异常状态 ⇔ 最后一个 ask 后面有 feedback（说明答完了），
           但后面没有新的 ask（说明补题失败）
```

修复时**只需补一条 `ask` 事件**，状态就自动变正确了。

**【原理】这就是 Event Sourcing 最实际的价值：它把「修复状态」变成了「追加事件」。**

如果用状态字段（`current_question_index`），这里要写：
判断字段与流水是否一致 → 找出该回退到哪 → 修正多个字段 → 保证其他字段也一致……
**这类「状态修复代码」是 bug 的重灾区。**

## 5. 事件表的设计

```328:348:backend/app/models.py
class KbTaskEvent(Base):
    """出题过程事件（#25 生题流式展示）。

    为什么用独立表而不是 `KbTask` 上的 JSON 列（D2）：
    - 写入：append 单行即可；JSON 列是「读整列→改→写整列」，事件多时 O(n²) 放大
    - 查询：`WHERE task_id=? AND seq>?` 走索引，天然支持 `since` 增量拉取
    - 清理：可按 task_id 单独删除，不必重写整列

    `seq` 为全局自增主键，单调递增，兼作前端增量游标。
    """
```

### 「JSON 列是 O(n²)」这句话的展开

```
用 JSON 列追加事件：
  第 1 个事件：读 0 字节   + 写 100 字节
  第 2 个事件：读 100 字节 + 写 200 字节
  第 n 个事件：读 (n-1)*100 + 写 n*100
  总计 = O(n²)     ← 事件越多越慢

独立表追加：一次 INSERT = O(1)
```

### `seq` 兼作游标

前端只需记住「我上次收到 `seq=17`」，下次请求 `since=17` 就拿到增量。

**【原理】这是所有流式接口的标准设计** —— 微博 timeline、Kafka offset、
GitHub Events API 都是同一个模式：**单调递增的游标 + 增量拉取**。

## 6. ⚠️ 一个可以改进的隐患

```143:149:backend/app/routers/chat.py
def _add_turn(db: ORMSession, s: ChatSession, role: str, turn_type: str, content: str, **kw) -> ChatTurn:
    seq = (db.query(ChatTurn).filter(ChatTurn.session_id == s.id).count() or 0) + 1
    t = ChatTurn(session_id=s.id, seq=seq, role=role, turn_type=turn_type, content=content, **kw)
    db.add(t)
    db.commit()
    db.refresh(t)
    return t
```

`seq = count() + 1` 是**「读后写」竞态**：

```
线程 A: count() = 5 → 打算写 seq=6
线程 B: count() = 5 → 打算写 seq=6
两个都写 seq=6 ← 冲突，事件顺序被破坏
```

现在因为 `chat_reply` 是串行调用的（一个人一次只发一条消息），暂时不会出问题。
但严格来说，正确做法是：

1. 给 `(session_id, seq)` 加**联合唯一约束**（数据库层兜底）
2. 或用 `MAX(seq) + 1` 配合乐观锁/重试

**【原理】凡是「先查询再据此写入」的逻辑，都要问：并发下会不会读到同一个旧值？**
这个模式叫 check-then-act race，是最常见的并发 bug 类型。

**这是个「知道就好」的点** —— 单会话单请求场景不必急着改，
但做多端（多人同时操作同一会话）时会成为真问题。

## 7. 本节小结

| 设计点 | 一句话原理 |
|---|---|
| 只存 `ChatTurn`，不存状态字段 | 事件溯源：状态是算出来的 |
| `_current_question` 投影 | 从事件流折叠出当前状态 |
| 三态状态机 + `MAX_PROBES` | 必须有权衡出口，防死循环 |
| hint/probe 共享计数 | 防止用提示绕过追问上限 |
| 评分失败 503 | fail-close：不确定就不要假装确定 |
| `next_failed` + 自愈 | 修复状态 = 追加事件 |
| 事件独立表 + `seq` 游标 | append O(1) + 增量拉取 |
| ⚠️ `count()+1` | check-then-act 竞态，需唯一约束兜底 |

## 8. 检索练习

**Q1.** 把 `probes_used` 变成 `ChatSession` 上的一个整数列，会失去什么？

**Q2.** 为什么 `hint` 和 `probe` 要共享 `MAX_PROBES` 计数？

**Q3.** 评分失败时抛 503 而不是给一个默认分（比如 60 分），体现了什么原则？

**Q4.** 「异常状态」在事件流里被表达成什么特征？为什么这让自愈代码很短？

**Q5.** `seq = count() + 1` 在什么场景下会真的出问题？

<details>
<summary>参考答案</summary>

**A1.** 失去三点：① 状态可能与流水不一致（字段说 2 次追问，流水里只有 1 条 probe）；② 无法从事件流完整重放（前端恢复现场时不知道追问是怎么发生的）；③ 自愈要改成「判断并修正字段」，代码复杂且易错。

**A2.** 如果各算各的，用户可以反复离题拿 hint、永远不进入评分。共享计数保证「补充轮次」是有限的总预算，用户必然在 2 轮内获得结果。

**A3.** fail-close 原则 —— 而且判断标准是「静默通过会不会误导用户」。给一个假分数比报错更糟：用户会以为自己答得还行，实际上系统根本没评。且因为不落 turn，状态未变，用户可重试。

**A4.** 表达为「最后一个 `ask` 之后有 `feedback`，但没有新的 `ask`」。因为状态由事件流推导，所以修复只需追加一条 `ask` 事件，状态就自动正确 —— 不需要写任何「修正字段」的逻辑。

**A5.** 同一会话被并发写入时（例如多端同时发消息，或未来加了「AI 主动追问」的后台任务）。两个请求都会 count 到同一个值，写入相同的 `seq`，破坏事件顺序，进而让投影算错。

</details>
