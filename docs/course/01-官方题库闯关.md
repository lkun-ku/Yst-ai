## 1. 心智模型：一局 = 一份快照

最朴素的实现是**无状态**的：

```
前端：给我 10 道职业理念的题
后端：随机查 10 条返回
前端：（用户做完）这是答案
后端：逐题判分
```

这个写法有个致命问题：**题目没有「归属」**。

用户答到第 7 题切后台、小程序被系统回收，再进来时那 10 道题已经找不回来了。
历史回看也不知道他当初答的是哪 10 道。想加「续答」「未提交不计数」这类需求全都做不了。

本项目的做法是**有状态**：把这一次练习建模成一个「局」，**先把题目 id 列表冻结下来**。

```python
sess = Session(
    candidate_id=c.id,
    module=module,
    knowledge_point=kp,
    question_count=len(selected),
    question_ids=json.dumps([x.id for x in selected], ensure_ascii=False),  # ← 关键
    mode=sess_mode,
    duration_sec=duration,
    deadline_at=deadline,
)
```

**【原理】快照（Snapshot）模式**：把一个易变的过程，在某一个时刻固化成一条不可变记录。
它一次性买到四个能力：

| 能力 | 靠什么实现 |
|---|---|
| 续答 / 弱网重连 | `GET /api/sessions/{id}` 按 `question_ids` 还原 |
| 历史回看 | `result_json` 存了每题的判定结果 |
| 幂等 | 重复提交直接返回缓存 |
| 限时考试 | `deadline_at` 存在服务端 |

**记住这句话：不要让「题目」飘在请求里，要把它钉在「局」上。**

## 2. 开局：三条分支

`start_session` 是一个分派器，按请求参数走三条完全不同的路：

```119:193:backend/app/routers/sessions.py

    if body.doc_id:
        # 分支 A：个人题库（用户上传资料生成的题）
    elif body.mode == "mock":
        # 分支 B：模考（按权重抽题 + 限时）
    else:
        # 分支 C：常规闯关（按模块或考点）
```

三条分支的差异：

| 分支 | 抽题范围 | 额度 | 限时 |
|---|---|---|---|
| A 个人题库 | 该资料的 `source=DOC` 题 | **不消耗**（边际成本为零） | 无 |
| B 模考 | 全池，按模块权重 | 消耗 | 45 分钟 |
| C 常规 | 指定模块 / 考点 | 消耗 | 无 |

**【原理】按场景分派而非参数堆叠**。三条路径的「抽题逻辑 + 权限 + 计费」都不同，
硬塞进一个函数会变成 `if doc_id and mode != mock and module...` 的意大利面。

⚠️ 注意分支 C 的一个细节：

```176:183:backend/app/routers/sessions.py

            q = q.filter(Question.module == body.module)
```

题库不足时**降级开局**而不是报错（`selected = _arrange(pool, body.question_count)` 里的 `min` 已在前面处理）。
这是项目里反复出现的降级哲学：**宁可少给，不可不给。**

## 3. 抽题：为什么必须分层抽样

```61:102:backend/app/routers/sessions.py
def _select_by_weight(db, n: int) -> list:
    """按官方模块权重抽题，尽量贴近真实卷面分布；题库不足时再补齐。"""
    out: list = []
    picked: set = set()
    for m, w in MOCK_WEIGHTS:
        need = max(1, round(n * w / 100))
        rows = (
            db.query(Question)
            .filter(
                Question.source == QuestionSource.POOL,
                Question.module == m,
                Question.proofread_status != ProofreadStatus.REJECTED,
            )
            .all()
        )
        if not rows:
            continue
        random.shuffle(rows)
        for q in rows[:need]:
            if q.id not in picked:
                out.append(q)
                picked.add(q.id)
    ...
```

权重来自真实卷面：

```41:48:backend/app/routers/sessions.py
#: 官方模块权重（%）：职业理念15 / 职业道德15 / 教育法律法规10 / 文化素养12 / 基本能力48
MOCK_WEIGHTS = (
    (Module.PROFESSIONAL_IDEA, 15),
    (Module.PROFESSIONAL_ETHICS, 15),
    (Module.EDU_LAW, 10),
    (Module.CULTURE_LITERACY, 12),
    (Module.BASIC_ABILITY, 48),
)
```

**【原理】分层抽样（Stratified Sampling）**：先按已知的总体结构把样本空间切成层，
每一层内部再随机。相比全局纯随机会：

- **保证结构正确**：基本能力占 48%，就真的抽 48%
- **降低方差**：不会出现某次模考全是文化素养的极端情况

如果纯随机抽 30 题，用户体验会是「这次考试全是文言文，下次全是逻辑推理」——
练出来的手感和真卷完全不一样。

后半段 `if len(out) < n` 是兜底：某个模块没题时从全池补足，**不让整局开局失败**。

### ⚠️ 已知缺陷：全表加载

`db.query(Question).filter(...).all()` 把**整个模块的题**拉进 Python 内存再 `shuffle`。
现在 418 题没感觉，题库扩到万级时每次开局要拉上万行、还要在 Python 里打乱。

改进方向（见第 06 节 P1）：

```python
# SQL 层随机抽样，不把数据搬到 Python
q.order_by(func.random()).limit(need)          # PostgreSQL / SQLite 3.35+
```

## 4. 判分：按题型分派 + 集合比较

```224:252:backend/app/routers/sessions.py
def _judge(q: Question, selected: list[str]) -> QuestionJudgement:
    qtype = str(getattr(q.type, "value", q.type) or "single")

    # 按题型分派：填空走文本归一化匹配；简答不自动判分；其余沿用集合比较
    if qtype == "blank":
        return _judge_blank(q, selected)
    if qtype == "short":
        return _judge_short(q, selected)

    correct_set = set(json.loads(q.answer))
    selected_set = set(selected)
    is_correct = selected_set == correct_set
    ...
```

**【原理】策略分派（dispatch）**：主函数只负责「路由到具体实现」，不负责具体判定。
新增题型时**只加一个分支 + 一个函数**，不改动已有逻辑。这就是「对扩展开放、对修改关闭」。

三个值得记住的设计：

### (a) 集合比较而非字符串比较

```python
is_correct = set(答案) == set(用户选的)
```

多选题选 `{A, B}` 和 `{B, A}` 判定相同 —— **顺序无关**。如果用字符串比对，
用户点击顺序不同就会判错，这是灾难性的。

### (b) 多选题有「半对」状态

```250:250:backend/app/routers/sessions.py
        state = "correct" if is_correct else ("partial" if correct_set & selected_set else "wrong")
```

`&` 是**集合交集**：非空说明至少选对一个 → `partial`（半对）。
漏选一个和完全选错，给用户的反馈不应该一样。

### (c) 填空题做文本归一化

```40:50:backend/app/services/validation.py
def normalize_answer(text: str) -> str:
    """填空判定的文本归一化（B2）：去空白、全角转半角、去句末标点、统一小写。

    用于「填对了却判错」的容错——用户画像对错误的容忍度低，误判会直接击穿信任。
    """
    s = str(text or "")
    for full, half in _FULL_TO_HALF:
        s = s.replace(full, half)
    s = re.sub(r"\s+", "", s)
    s = _END_PUNCT_RE.sub("", s)
    return s.lower()
```

用户填「教育的本质」，库里是「教育的本质。」—— 差一个句号就判错，用户会觉得产品很蠢。
**「填对了却判错」是这类产品最伤信任的 bug 类型，值得多写几行代码。**

### 简答题：诚实地「不判分」

```302:318:backend/app/routers/sessions.py
def _judge_short(q: Question, selected: list[str]) -> QuestionJudgement:
    """简答题：不自动判分（B1），标记 self_review 供前端展示自评提示。

    提交侧会跳过该题的掌握度更新与错题本写入，也不计入正确率分母。
    """
```

**【原理】不确定时不要假装确定。** 简答题用字符串匹配判分必然误判，
与其给一个错的分数，不如明确告诉用户「请对照参考答案自评」，
并且**把它排除出正确率分母**（否则统计口径就被污染了）。

## 5. 掌握度：EMA 的数学

```358:369:backend/app/routers/sessions.py
        m = (
            db.query(Mastery)
            .filter(Mastery.candidate_id == c.id, Mastery.module == q.module)
            .first()
        )
        if m is None:
            m = Mastery(candidate_id=c.id, module=q.module, score=0.0, attempts=0)
        m.score = round(m.score * 0.7 + (1.0 if j.is_correct else 0.0) * 0.3, 4)
        m.attempts += 1
```

**这一行是整个「自适应学习」的数学核心**：

$$
S_{n} = 0.7 \cdot S_{n-1} + 0.3 \cdot x_n, \quad x_n \in \{0, 1\}
$$

这就是 **EMA（Exponential Moving Average，指数滑动平均）**。

### 为什么不用「答对数 / 总题数」？

| 方案 | 问题 |
|---|---|
| 简单平均 | 用户开局错 10 题，之后全对，分数要爬很久才回来 —— **对进步不敏感** |
| 只看最近一次 | 一道题的偶然失误就让分数暴跌 —— **太抖** |
| **EMA** | 最近表现权重高（0.3）、历史有惯性（0.7）—— **既反映进步，又不被单次失误带偏** |

### 0.7 / 0.3 是什么

叫**平滑系数**。它决定「新信息占多大比重」：

```
0.7/0.3  → 平稳、迟钝（当前值）
0.5/0.5  → 灵敏、但抖动明显
0.9/0.1  → 几乎不动，学不动
```

**动手验证**：改这两个数，连续答对 5 题，看 `Mastery.score` 涨得多快。
（改完记得改回来 —— 仓库约定是改动前先建分支或 `git stash`。）

### ⚠️ 已知缺陷：粒度太粗

掌握度是按 `module` 存的（只有 5 个维度）。用户「职业理念」得 0.4，
但不知道是「教育观」差还是「学生观」差。**改造方向见第 06 节：降到知识点粒度。**

## 6. 幂等与防作弊

### 幂等（Idempotency）

```332:341:backend/app/routers/sessions.py
    # 幂等：已提交则直接返回缓存结果
    if sess.status == SessionStatus.SUBMITTED and sess.result_json:
        cached = json.loads(sess.result_json)
        return SubmitOut(
            session_id=sess.id,
            idempotent=True,
            results=[QuestionJudgement(**r) for r in cached],
            mastery=_snapshot_mastery(db, c.id),
            new_mistakes=[],
        )
```

**【原理】幂等 = 同一个操作执行多次，结果与执行一次相同。**

为什么必须有？网络超时是常态。用户在弱网下点了提交，没收到响应，
再点一次 —— 如果没有幂等保护，第二次会把每道题的掌握度**再加一遍**，
错题本的 `wrong_count` 也会翻倍。数据就脏了。

实现方式很朴素：**用状态位做闸门**（`status == SUBMITTED`），结果缓存进 `result_json`。

### 防作弊：服务端绝对时间

```404:410:backend/app/routers/sessions.py
    is_timeout = False
    if sess.mode == "mock" and sess.deadline_at:
        dl = sess.deadline_at
        if dl.tzinfo is None:
            dl = dl.replace(tzinfo=timezone.utc)
        is_timeout = datetime.now(timezone.utc) > dl
```

**【原理】永远不要相信客户端。** 如果后端返回「剩余 1800 秒」让前端倒计时，
用户把手机时间往前调一天就能无限延长考试。

正确做法：**服务端存绝对时刻 `deadline_at`，判定永远在服务端做**。
客户端的时间只用来渲染。

那个 `if dl.tzinfo is None` 是个具体的坑：SQLite 读回 `datetime` 会丢掉时区信息，
不做补全的话，`datetime.now(timezone.utc) > dl` 会抛 `TypeError`（naive 和 aware 不能比大小）。

编译接口时还额外返回了 `server_now` 给前端校正本地时钟：

```220:220:backend/app/routers/sessions.py
        server_now=_iso_utc(now),  # 供前端校正本地时钟
```

## 7. 额度：只限速，不限内容

```53:65:backend/app/routers/quota.py
def enforce_quota(db: DBSession, c: Candidate, requested: int) -> None:
    """发起闯关时校验免费额度；VIP 不限量。超限抛 429 友好提示。"""
    if c.is_vip:
        return
    used = used_today(db, c.id, date.today())
    if used + requested > FREE_DAILY_LIMIT:
        remaining = max(0, FREE_DAILY_LIMIT - used)
        raise HTTPException(
            status_code=429,
            detail=(
                f"今日免费额度已用完（{FREE_DAILY_LIMIT} 题，剩余 {remaining}），明天再来继续刷。"
            ),
        )
```

两个设计细节：

**(a) 用 429 而不是 403。** 429 = Too Many Requests（限流），403 = Forbidden（禁止）。
语义上「你今天刷够了」是限流不是禁止 —— 状态码要和语义匹配。

**(b) 个人题库不计额度：**

```26:38:backend/app/routers/quota.py
def used_today(db: DBSession, candidate_id: int, day: date) -> int:
    """今日已消耗额度：当日创建的闯关局 question_count 之和...
    B3：排除个人题库（module = 个人资料）的闯关局——题目由用户自己上传资料生成，
    边际成本为零，不应消耗每日免费额度。
    """
```

**【原理】按成本计费，而不是按动作计费。** 官方题是平台花钱生成的（要摊销），
个人题是用户自己上传资料生成的（平台边际成本≈0）。收用户两次钱是不合理的。

⚠️ 注意注释里提到的 **NULL 陷阱**：

```32:38:backend/app/routers/quota.py
    # 注意 NULL 陷阱：SQL 中 `NULL != x` 不为真，需显式把 module IS NULL 的局计入
    rows = (
        db.query(Session.created_at, Session.question_count)
        .filter(
            Session.candidate_id == candidate_id,
            or_(Session.module.is_(None), Session.module != Module.PERSONAL),
        )
```

模考局的 `module` 是 `NULL`（跨模块）。如果只写 `module != '个人资料'`，
SQL 里 `NULL != 'x'` 的结果是 `NULL`（不是 `True`），这些局会被静默漏掉 ——
**用户做模考不消耗额度**。必须显式写 `OR module IS NULL`。

**这是 SQL 里最经典的陷阱之一**，记住：`NULL` 参与任何比较都返回 `NULL`（三值逻辑），
要用 `IS NULL` / `IS NOT NULL`。

## 8. 本节小结

| 设计点 | 一句话原理 |
|---|---|
| `Session` + `question_ids` | 快照模式：把过程固化成不可变记录 |
| `_select_by_weight` | 分层抽样：保证卷面结构贴近真实 |
| 集合比较判分 | 顺序无关 + 支持「半对」 |
| `normalize_answer` | 归一化容错，避免「对了却判错」 |
| 简答不判分 | 不确定就说不确定，别污染统计 |
| `0.7/0.3` | EMA：兼顾灵敏与稳定 |
| `result_json` 幂等 | 重复提交不加倍计分 |
| `deadline_at` 服务端判定 | 永远不相信客户端 |
| `IS NULL` 显式处理 | SQL 三值逻辑陷阱 |

## 9. 检索练习

先合上答案自己想，再展开。

**Q1.** 如果把 `question_ids` 去掉，改成提交时才随机抽题，会破坏哪些已有能力？

**Q2.** `_arrange` 里「避免相邻同题型」的循环，为什么要从 `i + 2` 开始找而不是 `i + 1`？

**Q3.** 掌握度用 EMA 而不是简单平均，具体在什么用户行为下差异最大？

**Q4.** 额度的 `NULL` 陷阱如果没处理，用户会获得什么「免费的午餐」？

<details>
<summary>参考答案</summary>

**A1.** 破坏四个：① 续答/重连（重新进来无法还原同一套题）；② 历史回看（不知道当时做的是哪些题）；③ 幂等（重复提交会重新抽题、重复计分）；④ 模考公平性（每人的卷子不同，且可在提交前反复刷新刷到简单题）。

**A2.** 因为 `i + 1` 就是当前正在比较的那个位置（`selected[i]` 与 `selected[i+1]` 相比）。要替换的是 `i+1`，候选必须从 `i+2` 开始找，否则会把自己和自己交换，死循环或无效。

**A3.** 在「开局很烂、后面快速进步」的用户身上差异最大。简单平均会被前期的错误长期拖住，分数上不去，用户感觉「我明明都对了为什么还是不及格」；EMA 会较快反映进步。反过来，对「一直很稳偶尔失手」的用户，EMA 的波动更小。

**A4.** 做模考不消耗每日额度（`module IS NULL` 被静默漏掉），等于模考完全免费、不限量。

</details>
