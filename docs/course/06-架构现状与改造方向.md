## 2. 官方题库：不是「题少」，是「维度缺失」

### 2.1 三层表现

**① 绝对数量不够**

418 题 / 150 考点 ≈ **每考点 2.8 题**。用户在一个考点刷 3 次就见底了。
而模考权重里「基本能力」占 48%（`MOCK_WEIGHTS`），30 题卷要抽 ~14 道，
该模块只有 80 题 —— 连刷 6 场模考就会大量撞题。

**② 结构性缺失（比数量严重）**

教资实际是三科：

```
科目一 综合素质            ← 你现在 100% 在这里
科目二 教育知识与能力        ← 0
科目三 学科知识与教学能力    ← 0（按学科分：语文/数学/英语/...）
学段：幼儿园 / 小学 / 中学   ← 未建模（三科考纲都不同）
```

**这不是「多加点题」能解决的** —— 是 schema 层没有 `subject` / `stage` 这几个轴。
**不加轴就加题，1 万道题也会堆在一个格子里。**

**③ 质量污染（最紧急）**

⚠️ 两个风险点（第 2 个已在本轮修复，见 7.1 实施记录）：

```22:34:backend/app/seed/import_questions.py

                ...
                stem = f"下列关于《{kp}》的表述，正确的是？（种子变式{variant + 1}）"
                answer = json.dumps([correct], ensure_ascii=False)
                explanation = f"本题考查考点《{kp}》。正确选项为 {correct}：「{kp}」的核心要点如上所述。"
```

这是**占位模板题**（选项是「关于《XX》的正确表述 / 常见误解 / 无关表述 / 颠倒表述」），
毫无内容，却和真实题存在同一张表、同样 `source=POOL`、同样 `proofread_status=PASSED` ——
**抽题时无法区分**。

```50:63:backend/app/pipeline/batch_generate.py

                    Question(
                        ...
                        source=QuestionSource.POOL,
                        proofread_status=ProofreadStatus.PENDING,
                        aigc_flag=True,

                )
```

`LLM_MODE` 的**代码默认值**是 `fake`（`config.py`），但 `backend/.env` 把它覆盖成了
`real`（deepseek-flash）。所以「fake 模式灌假题」只在 `.env` 缺失或被改成 fake 时才触发 ——
CLI 默认拒绝执行（见 7.1 实施记录）。

**但真正的风险在 real 模式下同样存在**，而且更隐蔽。抽题只过滤 `!= REJECTED`：

```172:175:backend/app/routers/sessions.py

            Question.proofread_status != ProofreadStatus.REJECTED,  # 驳回即弃（票 13）

```

`batch_generate` 的产物是 `proofread_status=PENDING`，而 **`PENDING` 会被抽中**。
也就是说：**任何一次 real 模式的扩池，产出的 AI 题会立刻进入用户视野，先于人工审校。**

这是**既定设计**（`proofread.py` 的口径是「新题先上线，抽检驳回即弃」，
与项目「宁可降质不可失败」的哲学一致），不是 bug。但它的后果必须清楚：
**在 G2/G3 闸门（P2）落地之前，官方池的题只过了「结构校验」一道闸。**

> 实测数据（2026-05-17 于 dev 库）：官方池 418 道全部为 `PASSED`（2026-04-09 导入的真实题库）；
> 一次 `--per-kp 1` 的 real 模式扩池产出 121 道 `PENDING`（29 道被结构校验弃掉）。
> 这 121 道自写入那一刻起就是可被抽题命中的。

### 2.2 改造方向

**Step 1：先加维度**

```python
class Subject(str, Enum):
    COMPREHENSIVE = "综合素质"
    EDU_KNOWLEDGE = "教育知识与能力"
    SUBJECT_KNOWLEDGE = "学科知识与教学能力"

class Stage(str, Enum):
    KINDERGARTEN = "幼儿园"
    PRIMARY = "小学"
    MIDDLE = "中学"

# Question 新增列（全部可空，保证存量平滑迁移）
#   subject / stage / difficulty / source_kind / quality_score / kp_id / source_quote
```

**Step 2：知识点从「字符串列表」升级为「树」**

现在 `knowledge_point` 是扁平字符串，直接存在每题里（改一个字就断链）。
改成独立表：

```
模块(Module) → 章节(Chapter) → 知识点(KnowledgePoint)
教育法律法规 → 教育法体系 → 《义务教育法》免试就近入学
```

有了树才能做两件现在完全做不到的事：

- **覆盖度度量**：「考点 X 已有 3 题，考点 Y 有 0 题」一眼可见
- **知识点级掌握度**（现在掌握度只到模块粒度）

**Step 3：三层去重**

官方池现在**只有精确去重** `(module, kp, stem)`。
而文档出题侧已经有 Jaccard 近似判重（`doc_stem_dup_threshold=0.6`）—— **直接复用即可**。

| 层 | 手段 | 拦什么 |
|---|---|---|
| L1 精确 | `normalize_stem` 后比对 | 一字不差 |
| L2 近似 | 字符 3-gram Jaccard ≥ 0.6 | 「换种措辞」的重复 |
| L3 语义 | 题干 embedding 余弦 ≥ 0.92 | 题干不同但考点+干扰项同构 |

L3 专门防「AI 出题最典型的灌水」：同一考点换个背景故事又出一遍。

**Step 4：性能**

✅ **已改完（2026-06-15 核实）**。抽样的实现**收口在** `app/services/sampling.py`，
调用点是 `sessions._sample_pool` 与 `daily._get_or_create_task`：

```python
# 改造前（两处各写了一份）：全表拉进内存再 shuffle
rows = db.query(Question).filter(...).all()
random.shuffle(rows)

# 现在：只回真正需要的行
q.order_by(func.random()).limit(need)
```

**实测（1 万行题库、取 5 题、5 轮取中位）**：全表 `.all()` + shuffle **215.9 ms** →
SQL `LIMIT` **3.86 ms**（约 **56×**）。

📌 这段值得记住的不是数字，而是**过程**：改造时只改了 `sessions.py`，
`daily.py` 里**同一个写法漏了**（2026-06-15 核实性能欠账时才发现）。
所以现在抽样只有**一个**实现 —— 下次要抽，调用它，别再抄一遍。

## 3. AI 出题：根因在「上游」

### 3.1 一句话根因

**官方变式题链路上游没有任何知识源。**

```170:174:backend/app/services/llm_client.py
            prompt = (
                f'请出一道教资《综合素质》{module}模块考点《{req.knowledge_point}》的单选变式题，'
                '只输出 JSON：{"module":..., "knowledge_point":..., "stem":..., '
                '"options":[{"key":"A","text":...},...], "answer":["A"], "explanation":..., "type":"single"}'
            )
```

整个输入**就是一个考点名字**。模型只能从参数记忆里编。后果：

- 考点名模糊（如「教育机智」）→ 自由发挥 → 偏离考纲
- 涉及法条（如「教师平均工资不低于公务员」）→ 记错细节 → **事实性错误**
- 无法验证「答案是否唯一正确」

**反差**：文档出题链路（`kb_generate.py`）已有完整质量闭环 ——
检索 → 相关性评分 → 查询改写 → 自检 → 降粒度重试 → 补偿轮 → 溯源。

> **所以结论不是「AI 出题不准」，而是「有 RAG 的那条链路质量可控，
> 没 RAG 的那条链路必然出错」。**

### 3.2 教资考试的资料范围（知识源清单）

| 层级 | 资料 | 形态 | 用途 | 版权 |
|---|---|---|---|---|
| L0 考纲 | 教育部《考试大纲》三科 | 结构化条目 | **考点树的权威来源** | ✅ 政府公开 |
| L1 教材 | 中公/山香等 | PDF | 知识点正文 | ⚠️ 内部切片，不对外展示 |
| L2 法条 | 教育法/义教法/教师法/未保法… | 条文原文 | **法条题必须逐字引用** | ✅ 政府公开 |
| L3 知识点卡片 | 定义/关键词/易考角度/易混点 | 手写+AI 校 | 出题的 prompt 锚点 | 自产 |
| L4 真题分布 | 近 5 年真题的**考点频次**（不含原文） | 统计表 | 命题权重贴近真实 | ⚠️ 只要统计 |
| L5 备考 FAQ | 「综合素质怎么过」等 | 问答对 | 喂给问答老师 | 自产 |

> **本轮已确认的语料范围：L0 考纲 + L2 法条原文**（用户不提供教材 PDF）。
> 这两个恰好是版权最干净、且法条是出错率最高的区域 —— 投入产出比最高。

### 3.3 九步出题链

```
┌─ 离线阶段（跑一次，人工审一次）──────────────────┐
│ ① 考纲结构化 → 知识点树                          │
│ ② 法条/考纲切片 → official chunk（带 kp_id）      │
│ ③ 覆盖度仪表盘（哪个知识点 0 题）                 │
└───────────────────────────────────────────────────┘
                       ↓
┌─ 在线阶段（每次出题）────────────────────────────┐
│ ④ 选题规划：缺口 × 频次 × 错误率 − 疲劳度         │
│ ⑤ 证据检索：kp_id 硬过滤 + 语义召回               │
│ ⑥ 有据生成：考点卡 + 依据原文 + 题型规格 + 反例    │
│ ⑦ 四道闸门：结构 → 事实 → 唯一性 → 抽检           │
│ ⑧ 入库 + 溯源 + 覆盖度回写                        │
└───────────────────────────────────────────────────┘
```

**④ 选题规划的公式**：

```python
priority(kp) = w1 * 覆盖缺口          # 目标题数 - 已有题数
             + w2 * 真题频次          # 考得多不多
             + w3 * 用户错误率        # 该考点错题数 / 作答数
             - w4 * 最近已出次数      # 防疲劳
```

**【原理】这才是「覆盖考纲全部内容」的可度量定义** ——
不是一句 prompt 要求，而是一个**会收敛的配额系统**。

**⑦ 四道闸门**：

| 闸门 | 检查什么 | 手段 | 失败处理 |
|---|---|---|---|
| G1 结构 | 字段齐、选项互斥、答案在选项内 | 现有 `validation.py` | 弃 |
| G2 **事实一致性** | 每句话能否在依据里找到 | 法条/数字走**字符串硬匹配**，其余 LLM judge | 重生成 ≤2 次 |
| G3 **答案唯一性** | 是否存在第二个可辩护的正确项 | 独立作答 N=3 投票 | **弃**（不是重生成） |
| G4 抽检 | 随机 5% | 现有 `proofread.py` | 驳回 |

**G3 是最值得加的一道** —— 「AI 出题」最伤用户的不是答案错，是**争议题**：
两个选项都说得通，用户做错了觉得被坑。多模型投票能拦掉绝大多数。

**G2 的强化版**：法条/数字/年份类做**字符串硬校验** ——
题干里出现的法条引用必须逐字匹配 L2 原文库，不匹配直接弃。
**这比 LLM judge 可靠得多**（LLM 对「第几条、第几款」这种精确引用不可靠）。

### 3.4 三个额外提分点

1. **补回难度字段** —— 有了难度才能做自适应组卷
2. **干扰项质量** —— prompt 显式要求「干扰项必须来自本考点的常见误解（从易混点卡片取），
   不能是无关内容」。现在 AI 出的干扰项常「明显错误」，题目太送分
3. **自检不要自评** —— 换不同模型或不同 temperature 做自检，一致性会明显提高

## 4. 问答老师：缺的不是接口，是「官方知识库」

### 4.1 现状

项目**已有**：

- `kb_retrieval.retrieve_by_scope` —— 跨文档 RRF 混合检索
- `chat.py` —— 对话状态机、追问、评分

**缺的是**：`DocumentChunk` 全部隶属于某个 `candidate_id`：

```python
# Document 表
candidate_id: Mapped[int] = mapped_column(ForeignKey("candidates.id"), index=True)
```

**没有「公共知识库」这个概念**，所以检索只在「我上传的资料」里找。

### 4.2 共享机制

核心设计：**一个语料，两个命名空间，两个角色。**

```
                  ┌────────────────────────────────┐
                  │   Corpus 统一语料层             │
                  │   chunks 表 + kp_id + 命名空间   │
                  └───────────┬────────────────────┘
                              │
         ┌────────────────────┼────────────────────┐
         │                    │                    │
   namespace=official   namespace=personal   namespace=both
   考纲/法条             用户上传资料          （默认：先官方后个人）
         └────────────────────┼────────────────────┘
                              │
                  ┌───────────▼───────────┐
                  │  Retriever（共享）     │
                  │  向量 ⊕ 关键词 ⊕ kp过滤 │
                  │  → 返回 citations[]    │
                  └───────────┬───────────┘
                              │
             ┌────────────────┴────────────────┐
             │                                 │
     ┌───────▼────────┐              ┌─────────▼────────┐
     │  Teacher 角色   │              │  Examiner 角色    │
     │  问答老师       │              │  AI 出题          │
     ├────────────────┤              ├──────────────────┤
     │输出：解释+举例  │              │输出：结构化题目    │
     │     +引用       │              │     +溯源         │
     │允许说「不确定」 │              │答案必须唯一        │
     └───────┬────────┘              └─────────┬────────┘
             │                                 │
             └──── 讲完→练一练 / 做错→看讲解 ────┘
```

**共享的三样东西**（全部复用现有实现）：

| 共享件 | 现有实现 | 改动 |
|---|---|---|
| 检索层 | `kb_retrieval.retrieve_by_scope` | 加 `namespace` 参数 + `kp_id` 过滤 |
| 引用结构 | `DocumentChunk.content` / `heading_path` | 加 `page_no` / `char_start` / `char_end` |
| LLM 接缝 | `LLMClient.ask` / `.generate` | 加 `kind="kb_answer"` |

**落地最小改动**：给 `Document` 加两列 —— `owner_candidate_id`（可空）+ `is_official`。
`load_chunks` 的过滤条件从：

```python
.where(Document.candidate_id == candidate_id)
```

改成：

```python
.where(or_(Document.candidate_id == candidate_id, Document.is_official.is_(True)))
```

⚠️ **必须复核所有调用点，确认官方语料不会泄漏给越权用户**（`retrieve_by_scope_pg` 的 SQL 同样要改）。

### 4.3 职责边界

| | Teacher 问答老师 | Examiner AI 出题 |
|---|---|---|
| 目标 | 让用户「懂」 | 让用户「会做」 |
| 输入 | 自然语言问题 | (考点, 题型, 难度, 题量) |
| 输出 | 解释 + `citations[]` | JSON 题目 + 溯源 |
| 语气 | 通俗、举例、给记忆法 | 无语气 |
| 幻觉约束 | **必须能引到 chunk**；无依据时明说「资料里没提到」 | 信息必须全部来自 chunk |
| 不确定性 | 可以说「这个说法有争议」 | 不能：答案必须唯一 |
| 主动行为 | 可反问「你问的是 A 还是 B？」 | 不反问 |
| 出口 | 「要练几道这个考点的题吗？」→ **转出题** | 「看看讲解」→ **转问答** |

**那个互相跳转就是共享知识库的真正价值**：
讲的跟考的是同一批 chunk。**这是纯题库产品做不出来的闭环。**

### 4.4 准确率的四道保险

1. **拒答机制（最重要）** —— 检索 top-1 分数 < 阈值时，明确说「资料里没有」，
   而不是硬答。项目里已有 `RELEVANCE_THRESHOLD = 0.5` 可复用
2. **引用强制** —— prompt 要求 `citations` 非空，输出后校验每个 chunk_id 真实存在
3. **问题改写** —— 已有 `scope_rewrite_prompt` 可复用
4. **置信度分级** —— 「确定 / 大概率 / 存疑」，存疑的加「建议以官方教材为准」

| 维度 | 口径 |

| 不提供 | 下载 / 分享 / 复制接口 |
| 删除 | 用户删除资料时**物理删除** |

### 5.3 定位：现在做不到，因为页码丢了

```178:185:backend/app/services/doc_parser.py
    reader = PdfReader(path)
    pages: list[str] = []
    for page in reader.pages:
        try:
            pages.append(page.extract_text() or "")
        except Exception:
            pages.append("")  # 单页解析失败不中断整体
    raw = "\n".join(pages)
```

`"\n".join(pages)` 拼接时**页码信息彻底丢失**，`clean_text` 还主动过滤了纯页码行。
所以无法说「这段在第 12 页」，也无法高亮。

**解法分两步**：

```
Step A（低成本）
  parse_document 按页保留 → 记录 (page_no, char_offset_start, char_offset_end)
  DocumentChunk 加列 page_no / char_start / char_end
  → 能回答「第 12 页」，前端可跳页

Step B（体验更好）
  不做 PDF 内高亮（wx.openDocument 不支持）
  改用「双栏」：题目区 + 按 chunk 顺序渲染的原文段落流
  点题目 → 自动滚动到对应段落并高亮
  → 完全可控，不依赖 PDF 渲染器
```

### 5.4 溯源要补一环：`source_quote`

**现在有的**：

```
模型输出 source_id → picked_ids_of() 白名单校验（防幻觉编号）
  → 合法 → 存 Question.source_chunk = "[12]"
  → 非法/缺失 → 回退批级 "[12,35,41]"
```

**缺的**：只存了 id，前端展示「依据」要再查一次接口，且原文变更后断链。

**要补的**：

```python
Question.source_quote: str | None   # 生成该题所依据的原文原句（≤200 字）
```

出题时让模型回传 `quote`，校验 **`quote in chunk.content`**（子串校验）——
**这是防编造引用的杀手锏：模型编的句子不可能出现在原文里。**

## 6. 多端（安卓 / iOS）：现在不该做

### 6.1 三条路

| 方案 | 改动量 | 说明 |
|---|---|---|
| **A. Taro / uni-app 重编译** | 大 | 一套代码 → 多端。11 个页面要重写，**后端零改动** |
| **B. H5 + Capacitor 套壳** | 中 | 前端写 Vue/React 套壳成 App。**微信小程序代码不能复用** |
| **C. Flutter / RN** | 最大 | 完全重写前端 |

### 6.2 后端几乎不用动，但有两个例外

架构是对的 —— `routers/` 是纯 REST/JSON，身份靠 `X-Unionid` 头。要改的：

1. **登录体系** —— `unionid` 是微信小程序体系的，App 端没有。
   需要加手机号/微信开放平台 OAuth，`Candidate` 加 `phone` / `openid_app`，做**账号合并**
2. **语音** —— `voice.py` 依赖微信录音 API，App 端要换原生录音 + 服务端 ASR

### 6.3 真正的阻塞：后端不支持多实例

```28:35:backend/app/services/task_pool.py
def get_pool(name: str = GEN) -> ThreadPoolExecutor:
    """按用途取线程池（惰性创建）。"""
    pool = _pools.get(name)
    if pool is None:
        workers = settings.doc_embed_workers if name == EMBED else settings.doc_gen_workers
        pool = ThreadPoolExecutor(max_workers=max(1, workers), thread_name_prefix=name)
        _pools[name] = pool
    return pool
```

**`ThreadPoolExecutor` 是进程内的**：进程重启，在途任务全丢；多实例部署时任务无法协调。

多端意味着多实例，所以前置条件是：

```
任务队列外置（Celery / RQ / 云函数）+ Redis（队列与锁）+ PostgreSQL（已是生产方案）
```

**这件事无论做不做多端都该做** —— 它是「后端能不能上生产」的门槛。

### 6.4 建议

**先不做多端。** 理由：小程序留存还没验证完；而「后端多实例就绪」
这件事的价值远大于多端本身。顺序应该是：

```
后端多实例就绪 → 验证留存 → 再谈 Taro 复用
```

```
   └─ 官方池补 Jaccard 近似判重 + SQL 层抽样

P2 AI 出题升级（核心价值）
   ├─ 官方知识库：考纲 + 法条切片入库（is_official）
   ├─ variant 出题改造成 RAG（九步链）
   └─ 加 G2 事实一致性 + G3 答案唯一性闸门

P3 两个新功能

   └─ 原文可追溯（page_no + source_quote + 双栏渲染）

P4 后置
   └─ 多端：先做后端多实例就绪，再谈 Taro
```

### 7.1 实施记录

#### P0 止血（已完成）

**做了什么**：给两个「会污染官方池」的 CLI 入口加安全闸。**只加闸门，不改库、不改签名**。

| 文件 | 改动 | 效果 |
|---|---|---|
| `app/pipeline/batch_generate.py` | `main()` 改为 `main(argv) -> int`；`settings.llm_mode != "real"` 且未传 `--allow-fake` 时拒绝执行并返回退出码 2 | fake 模式的占位题不再能写进官方池 |
| `app/seed/import_questions.py` | `main()` 改为 `main(argv) -> int`；未传 `--allow-placeholder` 时拒绝执行 | 占位模板题不再能经 CLI 灌入 |

**为什么闸门加在 `main()` 而不在库函数里**：

- `batch_generate(db, per_kp, client=...)` 与 `import_questions(db, items=...)` 被**测试大量直接调用**
  （`tests/` 里有十几处 `import_questions(db_session)` 作为夹具），加闸会整片打破
- 真正的footgun 是**CLI 调用**（`python -m app.pipeline.batch_generate`），库函数不会自己跑起来
- 结论：**在「人能误触的入口」设闸，而不是在「程序调用的接口」设闸**

**回归测试**（`tests/test_pipeline.py` 新增 3 例）：

| 用例 | 断言 |
|---|---|
| `test_batch_generate_cli_refuses_fake_mode` | fake 模式返回 2，输出含「拒绝执行」「占位模板题」 |
| `test_batch_generate_cli_allows_real_mode` | real 模式放行返回 0（用桩替换落库，不真调 API）—— **确保闸门不误伤正常路径** |
| `test_seed_cli_refuses_placeholder` | 返回 2，且提示了 `import_real_bank` 这条正确路径 |

**验证结果**：`python -m pytest -q` 全量通过（exit 0）。

#### P0 未覆盖的部分（留给 P1）

- **`build_questions()` 的默认状态仍是 `PASSED`**，占位模板题在库里无法与真实题区分。
  彻底修法要等 `Question.source_kind` 列（P1）—— 用 `source_kind="seed_template"`
  做**结构性区分**，比靠调用方自觉可靠
- **`PENDING` 立即可抽题命中**（见 2.1 ③）。这是既定设计，真正的解法是 P2 的 G2/G3 闸门
  与 P1 的 `quality_score` 抽题降权，而不是改过滤条件

#### 顺带发现的存量数据问题

dev 库中存在**悬挂引用**（非本轮改动造成，`import_real_bank.py --clear` 只清 `questions`
不清理引用它的表）：`mistake_book` 19 条、`error_reports` 2 条指向已不存在的题目。

改造时若要做「错题本按考点复习」等联表逻辑，需先加外键级联或做一次清理。

### 排序逻辑

| 优先级 | 判断依据 |
|---|---|
| P0 最高 | **已经在伤害用户**，且修复成本极低 |
| P1 次之 | 是 P2/P3 的**前置依赖**（没有维度就无法规划选题） |
| P2 高 | 直接影响产品质量的核心价值 |

| P4 低 | 用户明确说「只是想法」，且前置条件未满足 |

## 8. 实施时的防回归清单

- ⚠️ **`OFFICIAL_MODULES` 常量不可绕过** —— 任何表达「官方模块」语义的地方必须用它，
  禁止直接遍历 `Module`（仓库既有约定）。新增科目后要复核该常量的所有使用点
- ⚠️ **Enum 加值的迁移风险** —— `Module` / `QuestionType` 是 SQLAlchemy `SAEnum`，
  新增 `Subject` / `Stage` 时 SQLite 要 `ALTER TABLE`，PG 要 `ALTER TYPE ... ADD VALUE`，
  **Alembic 里必须分方言处理**
- ⚠️ **检索层改动面** —— `load_chunks` 过滤条件放宽后，
  必须确认**不会把官方语料泄漏给越权用户**（`retrieve_by_scope_pg` 的 SQL 同样要改）
- ⚠️ **Fake 实现必须同步** —— 新增 `kind` 后必须补 `FakeLLMClient` 分支，
  否则 `LLM_MODE=fake` 下全链路测试会**静默降级为无产出**，掩盖真实问题
- ⚠️ **LLM 成本** —— G3 唯一性投票是 3 倍开销。用配置开关控制，
  只对官方池启用，个人资料题不启用
- ⚠️ **向后兼容** —— 新增列全部可空；`QuestionOut` 只加字段不删，
  避免小程序端解析失败

**验证纪律**（仓库约定）：每阶段跑 `python -m pytest` 全量 + 前端 `node --check`；
改动前建分支或 `git stash`。

| 模块 | 真实瓶颈 | 根因 |

## 10. 检索练习

**Q1.** 为什么说题库问题是「维度缺失」而不是「数量不足」？

**Q2.** AI 出题的根因是什么？为什么解法在「上游」而不是「换更强的模型」？

**Q3.** 为什么法条类题目要用「字符串硬匹配」而不是 LLM judge？

**Q4.** G3 答案唯一性投票失败时，为什么处理方式是「弃」而不是「重生成」？

**Q5.** 多端兼容的真正阻塞是什么？

<details>
<summary>参考答案</summary>

**A1.** 因为 418 题堆在一个格子（科目一）里，加题只增加同一格子的密度；而用户需要的其他格子（科目二、科目三、各学段）**一个都没有**。没有 `subject`/`stage` 两个轴，加到 1 万题也还是只有科目一。

**A2.** 官方变式题的 prompt 只有一个考点名，**没有任何源材料**，模型只能凭参数记忆编。换更强的模型只是降低出错概率，不能**验证**对错；而上游给依据后，答案可以逐句核对、可溯源、可校验 —— 这是从「概率正确」变成「可验证正确」。

**A3.** LLM 对「第几条、第几款」这类精确引用不可靠（容易记错或改写措辞），而字符串匹配是**零误判**的。原则是「能用确定性手段解决的问题，不要交给概率模型」。

**A4.** 因为 G3 失败意味着**这道题本身有缺陷**（两个选项都能说得通），不是「生成得不好」。重生成可能再次产生争议题，而这道题无论怎么改都不适合给用户做 —— 直接弃掉更干净。

**A5.** 后端 `task_pool` 是**进程内的** `ThreadPoolExecutor`：进程重启任务全丢，多实例无法协调。多端意味着多实例部署，所以必须先把任务队列外置（Celery/RQ + Redis）。

</details>
