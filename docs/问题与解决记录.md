## 这份文档怎么读 / 收录标准

只收**有记录价值**的问题，不收"我们实现了某功能"。具体是这六类：

| 类别 | 为什么值得记 |
| --- | --- |
| **反直觉的实测结果** | 「优化」实测是负收益而被否决 —— 结论与直觉相反，才说明度量真的在起作用 |
| **由自动化检查跑出来的 bug** | 不是读代码看出来的，说明工具链比人眼可靠 |
| **静默失效** | 不报错、不白屏，只是结果悄悄错了 —— 这类最危险，也最难靠人发现 |
| **前提失效导致的反转** | 开工前核查发现"计划里的前提不成立"，于是改做法而不是硬做 |
| **"未验证"声明** | 环境限制导致某条路径只能登记为未验证，而不是假装做完了 |
| **文档与事实不符** | 失效引用、索引与磁盘不一致、口径反转 —— 影响的是"去哪找依据" |

每条按 **现象 → 根因 → 做法 → 代价 → 数据 → 出处** 写。
**所有基准数字都注明模式**：本仓基准多在 `fake` 模式下取得，它们证明"链路通、指标算得出、判据生效"，
**不是**"真实模型下答得准"的证据。

## 1. 领域建模：一个枚举值引发的连锁错误

### 1.1 科目二"一个枚举值 = 一科"是根本性错误

- **现象**：P1 把 `Subject` 写成 `COMPREHENSIVE / EDU_KNOWLEDGE / SUBJECT_KNOWLEDGE`，用单一 `EDU_KNOWLEDGE` 指代科目二。当时以为"只是命名不规范"，实际是**指代范围错误** —— 官方口径下科目二随学段改名（幼儿园《保教知识与能力》7 模块 / 小学《教育教学知识与能力》7 模块 / 中学《教育知识与能力》8 模块），任何按科目做的统计与组卷都会**把三个学段的题混在一起**。
- **根因**：单一枚举值覆盖了三套不同的考纲；`KnowledgePoint.code` 用中文科目名做前缀（`综合素质/职业理念/教育观`），在科目二上必然歧义。
- **做法**：`Subject` 改为「科目序号 × 学段 → 领域包」，枚举值 = 领域包目录名；新增 `SUBJECT_META / PAPER_CODES(101/201/301) / subject_of() / paper_code_of()`；清空存量后用种子脚本重建。
- **代价**：数据不可恢复（删 `questions` 1009 行 + 错题本 + 纠错记录）；`Module` 枚举仍是科目一专属，科目二 8 个模块无枚举表示。
- **数据**：迁移 `questions` 1009 → 0、无悬空引用；种子重建 **155 节点**；改后 pytest 264 passed。
- **出处**：`docs/adr/0011-领域模型纠偏.md`、`CONTEXT.md`

### 1.2 枚举"能存、不能读"的延迟爆雷

- **现象**：`subject/stage` 由 `SAEnum(native_enum=False, create_constraint=False)` 渲染 → 落库是 `VARCHAR(32)`，**数据库侧无任何 CHECK 约束**。旧成员名 `COMPREHENSIVE` 能安然躺在列里，直到**读**的时候才由 Python 侧抛 `LookupError`。当时以为"用了枚举就类型安全"。
- **根因**：Python 侧校验只守写入，数据库层不设防。
- **做法**：清空而不回写（旧值覆盖三学段，**无法无歧义回写**）；两类枚举**分方言迁移**（`Subject/Stage` 是 VARCHAR 无需 DDL；`QuestionType` 在 PG 上是原生 ENUM，需 `ALTER TYPE ... ADD VALUE`）。
- **代价**：**数据库层不设防**被记为已知代价；`create_constraint=True` 未采纳（需重建表，且与"新增列一律可空"的升级期约定相互牵扯）。
- **出处**：`docs/adr/0011`

### 1.3 领域包：两份真相 + 一个 YAML 字面量陷阱

- **现象**：`pack.yaml` 原本重复声明 `no/name/stages/paper_codes`，与 `models.SUBJECT_META` 构成**两份真相**；且 `pack.yaml` 写 `no: 1` **取不到值** —— YAML 1.1 把 `no` 当布尔字面量，键被解析成 `False`（表现为 `no=0`）。两个都是**自查**发现的。
- **做法**：**身份在代码、内容在数据** —— 身份（枚举/序号/名称/覆盖学段/试卷代码）权威在 `models.py`；内容（模块/权重/题型/考纲版本）在 `pack.yaml`；loader 把身份**注入** `Pack`。四条不变量在加载期即报错（目录名==key；key∈枚举；题型∈`QuestionType`；声明权重的包权重和==1.0）。
- **代价**：「加科目 = 加一个枚举成员 + 加一个目录」，**不是"零代码"** —— 用"改一行代码"换回静态类型与迁移可控性。`k2_middle` 有两处**显式留白**（未映射枚举、未标权重），**留白是决策不是遗漏**。
- **数据**：四条不变量各有用例守着；`k1_comprehensive` 权重和 1.0（0.15/0.15/0.10/0.12/0.48）。
- **出处**：`docs/adr/0012-领域包结构与职责边界.md`、`docs/改造计划.md` §3.1

### 1.4 复盘维度会"自动变六维"（既有缺陷）

- **现象**：`review.py` 遍历 `Module` **全枚举** → `PERSONAL` 加入后五维雷达**会自动变六维**。
- **做法**：官方闭环保五维（排除 `PERSONAL`），个人题闯关给简化复盘；**任何官方统计遍历 `OFFICIAL_MODULES`，绝不遍历 `Module`**。
- **出处**：`docs/项目技术深度文档.md` §6.4、`CONTEXT.md`

## 2. 检索：三个反直觉的实测结果

> 这三个是本项目**最有价值的负结果**。它们的共同前提是：**先有尺子，才有结论** —— 没有第 2 项建的评测体系，"换了没用"也只能是猜测。

### 2.1 稀疏通道"升级为 BM25"被实测**否决**

- **现象**：教科书写法的"升级"（二元组命中数 → BM25）实测**全面更差**。预期是"编号类查询 recall@k 提升"，实际相反。
- **根因**：**IDF 的前提"罕见 ⇒ 信息量大"在本场景不成立** —— 法名的字组（`育法`/`法第`）**不在条文正文里**（法名只出现在 `heading_path`），IDF 很高却匹配不到任何片；条号的字组（`第一`/`一条`）每部法都有，df 并不低。**IDF 压掉的恰好是唯一还能用的信号**。
- **做法**：保留"命中数"口径；BM25 代码**不删**（`keyword_rank_bm25` 仅作对照，评测表留三档专为"被否决的升级"存档）；新增一条**锁住回退决定**的断言 `test_生产入口用命中数口径而不是BM25`。
- **代价**：参数扫遍（b∈{0,0.3,0.6,0.75} × k1∈{0.5,1.5,3}）仍差一倍以上，继续调就是"为了让结论好看而调"。
- **数据**（n=135，fake 模式）：② 命中数 recall@1 **0.7111** / MRR 0.8227 vs ③ BM25 **0.2593** / 0.4494；去偏袒纯编号复测 ② 0.4000 vs ③ 0.1000~0.1833。
- **出处**：`docs/adr/0015-稀疏通道保留命中数口径并否决BM25.md`

### 2.2 精排"只喂正文"比不精排**还差**

- **现象**：精排初版默认只喂正文（出于"别把答案抄给模型"的测量卫生考虑），实测**否定了这个默认值**：recall@1 **0.5630**，比不精排（0.7111）**低 0.148**。一个"聪明"的模型做了错误判断 —— 它分不清「教师法第七条」与「未成年人保护法第七条」，于是把**语义更像**的那条排上来。
- **根因**：与 2.1 **同源** —— 法名与条号只出现在 `heading_path` 里，正文里没有。
- **做法**：**必须把 `heading_path` 一起喂给模型**；且必须**声明增益来源**（含标题的增益主要来自元数据，不是 Cross-Encoder 的语义理解）—— 两种口径**并排报**，不合并成一个数字。
- **代价**：引入 266MB 非仓库资产（第一次引入"需额外准备"的运行时能力）；`rerank_pool=20` **未扫过参**；延迟未测。
- **数据**（n=135）：不精排 0.7111 → 仅正文 **0.5630** → 含标题 **0.8000** / MRR 0.8753。增益 +0.0889 = 上限 0.2815 的约 **32%**。**上限先算**：`recall@20 − recall@1`。
- **出处**：`docs/adr/0016-精排引入裁决与喂给模型的内容.md`

### 2.3 标题加成在小语料上是**负收益**

- **现象**：第 ④ 档"+RRF+标题加成"**就是当前 SQLite 生产路径的真实行为**，它比第 ③ 档更差 —— recall@2/@3 从 1.0 掉到 **0.9333**，说明标题加成**把一条本该召回的结果挤出了 top-3**。当时以为标题加成只会更好。
- **根因**：该语料 `heading_path` 是**文件名**（`教育学基础`/`综合素质`），而成按二元组命中计分 ——「教育」「综合」命中**整份文档的所有切片**，给非黄金切片一起加分。
- **做法/代价**：记为未决；**不能直接外推到生产**（真实语料是章节标题），须在官方语料入库后复验 —— ⚠️ **本期未单独结题**，它仍在生产路径上。
- **数据**：6 片语料 / 15 查询：③ 档 recall@2/@3 = 1.0；④ 档 = 0.9333。
- **出处**：`docs/改造计划.md` §3.2 发现 1、§5 未决第 6 项

### 2.4 PG 生产路径"只走向量通道"的静默缺陷

- **现象**：PG 路径（生产）**只走向量通道**，关键词不参与融合。当时的理由是"生产 chunk 全部有 embedding，可接受" —— 这个推理**只覆盖了"能不能召回"，没覆盖"召回得准不准"**。另外 query embedding 失败时**直接返回空**，把"部分能力可用"误报成"没有数据"。
- **做法**：改双通道 —— 向量（HNSW + SQL 余弦）+ 关键词（SQL `LIKE` **粗筛**候选 → 应用层精算）→ RRF 融合；两路**等深**；embedding 失败改为只走关键词通道。
- **数据**：生产配置相对纯向量 recall@1 **0.4296 → 0.6667**、MRR 0.5353 → 0.7703（这是"纯向量对编号类查询必然失败"的第一次量化）。
- **出处**：`docs/adr/0015`、`docs/改造计划.md` §4

### 2.5 基准数字**跨进程不可复现**（比基准不准更危险）

- **现象**：标注生成的排序键写成 `key=lambda t: -df.get(t, 0)` —— **不完整**。`df` 相同的词项先后取决于 `set` 迭代顺序，而它取决于字符串哈希、CPython **默认按进程随机化**。后果：跨进程生成的标注不同 → **基准数字每次运行都不一样，而且不报错**。同一份代码跑出 ⑤ recall@1 = 0.6667 与 0.3037（dense 更从 0.4296 掉到 0.0074）。
- **根因**：**基准不可复现比基准不准更危险** —— 不准至少是稳定地错、可被发现；不可复现会让每次运行给出新数字，于是"改进"与"噪声"无法区分。
- **做法**：① 排序键补次级键 `(-df, t)`；② 新增 `labels_fingerprint()` 把标注摘要写进 metadata；③ **新增跨进程可复现性测试**（用两个不同 `PYTHONHASHSEED` 的子进程生成标注并要求指纹一致 —— **这是唯一能真正钉住这类问题的方法，同进程内重复调用测不出来**）。
- **代价**：**撤回**原用"⑤ > ⑦"佐证"生产配置优于 BM25 版"那条论据（结论收窄但不改变）；新增一条纪律 —— **任何写入 ADR 的数字，必须先证明它可跨进程复现**。
- **数据**：指纹 `c546386e7906`（PYTHONHASHSEED 0/1/默认三进程一致）；② 0.7111、③ 0.2593 三进程稳定。
- **出处**：`docs/adr/0015` 勘误（2026-06-11 追加）

## 3. 防幻觉与引用校验

### 3.1 "是否编造"是布尔问题，不该用概率方法猜

- **现象**：产品硬承诺"句句有出处"，但**既有防线全是概率性的** —— 提示词是请求不是保证；LLM judge 自己也会幻觉；**语义相似度对编号级篡改完全无感**（「第七条」与「第八条」相似度能到 0.9+）；人工抽检无法覆盖全量。而这类错误**不会报错**：生成照常返回、界面照常渲染。
- **做法**：强制 `source_quote` + 子串硬校验，五态判定 `exact / normalized / fabricated / too_short / missing`；**剥书名号前缀但条号必须参与比对**（剥了会让"正文对、出处错"通过，那正是最该抓的一类）；闸门位置在**规则校验之后、LLM 自检之前**（成本顺序）。
- **代价**：**概括与意译会被误杀**（容忍范围只有标点/空白/全半角/书名号）—— 刻意方向，宁可误杀不可漏放。
- **数据**：**378 条用例**（正 184 / 反 194），拦截率 **1.0（194/194）**、流出编造率 **0.0（0/184）**、误杀率 0.0；命中层级 逐字 49 / 归一化 135（**逐字占比 0.2663**）。
- **出处**：`docs/adr/0014-引用校验用子串硬匹配.md`、`backend/eval/results/citation_baseline.md`

### 3.2 `too_short` 与 `fabricated` 必须分开（指标诚实性）

- **现象**：`第七条` 这种三字引用在原文里**逐字存在**，按真值定义**它是真实引用**。若把它记成"编造"，会让"零编造"这个指标变得不诚实 —— 把"引用太短"和"凭空捏造"算成一回事，数字好看但含义被污染。
- **做法**：`too_short` 有独立状态与计数（被拦的理由是"不能作为证据"，属**产品政策**而非真假判定）。
- **代价**：反例真值用「**精确子串缺席**」独立判定，**不用校验器自己的归一化逻辑** —— 否则等于让被测对象自己出考卷。
- **出处**：`docs/adr/0014`

### 3.3 "只看流出编造率 = 0"是自欺

- **现象**：闸门未触发时"流出编造率"同样是 0 —— 一个**关掉的闸门**与一个**有效的闸门**在数字上完全一样。
- **做法**：指标**成对**上报；`sound` 定义为「拦截率 > 0 **且** 流出编造率 = 0」。同理拒答率**拆两个方向**（误拒率 vs 正确拒答率）。
- **出处**：`docs/adr/0014`、`backend/eval/results/teacher_baseline.md`

### 3.4 引用校验被"章标题混入条文正文"绕过（**由基准跑出来的真 bug**）

- **现象**：切片取「本条开头 → 下一条开头」，而两条之间可能隔着**下一章的标题**，于是 `## 第二章 权利和义务` 成了第一章末条的**正文**。后果：① 检索污染；② **引用校验被绕过** —— `source_quote` 可以引用一段章标题，而它会因为"确实出现在该片正文里"通过硬校验。
- **做法**：切片期 `_trim_trailing_chapter` 切掉它。
- **代价/启示**：**这个 bug 不是靠读代码发现的** —— 是一条"删中间字"用例漏放，追下去发现差异全在 `\n\n##` 这几个非可读字符上。
- **出处**：`docs/adr/0014` §7、`docs/改造计划.md` §3.3

### 3.5 假客户端必须摘**真实原文**作为引用

- **现象**：若 fake 给的引用定位不到，`LLM_MODE=fake` 下**所有题都会被闸门拦掉**，测试将再也覆盖不到闸门之后的链路 —— **等于把下游一起"测没了"**。
- **做法**：`FakeLLMClient` 从出题提示词的切片块里**原样摘录**一句；没有切片可摘时返回"未给引用"，**不编一个来充数**。
- **出处**：`docs/adr/0014` Decision 5

## 4. 出题质量闸门

### 4.1 引用校验只看"主动申报"，模型不申报就绕过

- **现象**：`source_quote` 是模型**自己声明**的依据；模型完全可能**不在** `source_quote` 里申报，却把一条法条直接写进题干（如"根据《教师法》**第八十七条**…"）。当时以为引用校验能拦住编造法条。
- **做法**：G2 事实一致性 —— 扫题干/解析/选项里的全部「《X》第 N 条」，**条号必须精确**（判据是 `heading_path` 最后一段**恰好等于**该条号，`《教师法》第七十七条`不能因库里存在`第七条`就算命中）；法名允许简称但**必须出现**。零成本硬匹配。
- **数据**：新增 21 用例，其中 `test_条号必须精确_第七十七条不能靠第七条蒙对` 是红线。
- **出处**：`docs/adr/0018-出题质量闸门G2与G3.md`

### 4.2 已有 LLM 自检"看着答案"评分，测不出歧义

- **现象**：原自检把题干、选项、答案、解析一起给模型问"是否忠于资料"。它对「**答案本身有歧义**」完全不敏感 —— 一道模棱两可的题，答案写成哪个它都说"对"。
- **做法**：G3 **盲答** N 次（只给题干与选项）：N 次不一致 → 有歧义；N 次一致但与自带答案不符 → **答案是错的**（更严重）。**默认关闭**，只在"高价值题"上开。
- **代价**：**N 倍成本**；4 条防误杀细节（无效投票丢弃、多选键序归一化、非选择题型直接放行、替身必须能走通成功分支）。
- **数据**：⚠️ **G3 成本未实测**；**只在 fake 模式下验证过**，真实模型下拦截率**无数据**。
- **出处**：`docs/adr/0018`

### 4.3 闸门顺序即成本顺序

- **做法**：`G1 结构校验 → 引用硬校验 → G2 事实一致性 → LLM 自检 → G3 唯一性投票`（零成本 → 零成本 → 零成本 → 高成本 → N 倍成本）。前四道砍完之后，只剩"值得花 N 倍成本"的题进 G3。
- **关键约束**：闸门**不随** `enable_loop` 开关 —— 否则编排 A/B 对照会混入第二个变量。
- **出处**：`docs/adr/0018`

### 4.4 占位假题污染官方池（"已在伤害用户"）

- **现象**：种子题是模板占位假题，却和真实题存在同一张表、同样 `source=POOL`、同样 `proofread_status=PASSED` —— **抽题时无法区分**。
- **更严重的一层**：`batch_generate` 产物是 `PENDING`，而**`PENDING` 会被抽中**（抽题只过滤 `!= REJECTED`）→ **任何一次 real 模式扩池，产出的 AI 题会立刻进入用户视野，先于人工审校**（这是既定设计，不是 bug）。
- **做法**：P0 止血 —— CLI 入口加安全闸（`llm_mode != "real"` 且未传 `--allow-fake` 时拒绝执行）。**闸门加在 `main()` 而不在库函数里**，因为库函数被测试大量直接调用，而**真正的 footgun 是 CLI**。
- **数据**：官方池 418 道全 PASSED；一次 `--per-kp 1` 的 real 扩池产出 **121 道 PENDING**（29 道被结构校验弃掉），这 121 道**自写入即命中**。
- **出处**：`docs/course/06-架构现状与改造方向.md` §2.1③/§7.1

### 4.5 官方变式题链路上游"零知识源"

- **现象**：官方变式题的 prompt **整个输入就是一个考点名字** —— 模型只能从参数记忆里编。后果：考点名模糊 → 偏离考纲；涉及法条 → 记错细节；无法验证答案唯一。当时以为是"AI 出题不准"。
- **根因**：**官方链路零 RAG**（而文档出题链路已有完整质量闭环）。
- **结论**：**有 RAG 的链路质量可控，没 RAG 的链路必然出错** —— 解法在"上游"（补知识库 + 闸门），**不在"换更强的模型"**。
- **出处**：`docs/course/06-架构现状与改造方向.md` §3

## 5. 编排与 Agent：四处"前提不成立"

### 5.1 "框架能提升质量"被受控实验**否定**

- **现象**：需求定了 LangGraph，但出题管线是**线性的**（解析→清洗→切分→embedding→检索→分批生成→校验→去重→落库），没有多步 agent/条件分支/工具调用。当时以为"框架能带来质量提升"。
- **做法**：代码级实现三条路线（**共享同一检索/提示词/LLM 接缝/校验，唯一差异是编排层**）做受控对比。
- **结论**：**框架对效果中立** —— 选 LangGraph 不损失质量，仅取可扩展性；成本代价明确：闭环每题 LLM 调用约为 baseline 的 **7 倍**。
- **数据**：fake 下 ②③ 五维均 4.0、调用均 72（**逐项相等**）；real 下事实性 4.875 → 5.000，每题调用 **0.57 vs 3.88/4.21**。
- **出处**：`docs/adr/0009-知识库出题编排框架引入裁决.md`、`docs/RAG路线三落地复盘.md` §3.1

### 5.2 "改造 `chat.py` 为有据答疑"——读完代码后前提不成立

- **现象**：计划写"改造 `chat.py`"。但读完全文发现它是完整的**面试训练闭环**（面试官出情境题 → 考生答 → 追问链 → 终评给分落库），训练的是"**答**"；而有据答疑解决的是"**问**"。改造它等于**替换**这个功能，不是增强。
- **做法**：新建 `teacher_agent` / `tools` / `prompts_teacher` + 路由，`chat.py` **一字未动**；计划要求的"保留无据版作对照"改为**做成模式**（`mode="plain"`）而非留旧端点 —— 对照实验要控制变量，**留旧端点会把"提示词漂移"混进差异里**。
- **数据**：基准 25 问（可答 20 + 不可答 5），引用首次通过率 grounded/agent **均 1.0**（fake 模式）。
- **出处**：`docs/adr/0017-问答老师用新模块而非改造chat.md`

### 5.3 "只数有没有材料"当有据判据 → 实测正确拒答率 = 0

- **现象**：计划流程图写「超限或仍不足 → 拒答」。但"有据"的判据太弱 —— **"只数有没有材料"几乎恒真**（检索永远返回 top-k），**实测正确拒答率 = 0**。
- **做法**：拒答**只看证据不看轮次**（超限但有材料 → 作答；未超限但没材料 → 拒答）；sufficiency **由证据算、不由模型自称**（模型说"够了"只用于结束循环）；补一道**相关性下限闸门**。
- **代价**：相关性下限只挡"与库完全无词形重合"一类，**挡不住"像真的但库里没有"**（问《民法典》而库里只有教育法条）；语义级判定**本项未做**。
- **评价**：`正确处理拒答率 = 0` 被标为**本次最有价值的发现** —— 它说明失效会一直潜伏到真实用户身上才暴露。
- **出处**：`docs/adr/0017`、`docs/改造计划.md` §3.3 结论 3

### 5.4 原生 function calling 被暂缓（不可离线测试）

- **现象**：原生 `tools=[...]` 更省一次解析，但本仓 `LLMClient` 是**纯文本接缝**不是 `BaseChatModel`，且原生工具调用**无法离线测试**（fake 下没有真实供应商）—— 必然成为又一条"只能标注未验证"的分支。
- **做法**：工具决策用**结构化文本契约**（任何模型都能用，Fake 能给出确定性决策）。
- **反转条件**：若原生 function calling 变得可离线测试应换回。
- **出处**：`docs/adr/0017` Decision 4

### 5.5 `lookup_law` 堵住"第七十七条当第七条"

- **现象**：`LIKE %第七条%` 会命中「第七十七条」，于是把模糊命中当答案。
- **做法**：SQL 粗筛之后**必须在应用层复核条号段是否精确相等**；复核全灭时**如实返回空**。这个工具是 2.1/2.2 那个结构事实的收口 ——「《教师法》第七条」这类问题本质是**结构化查询**，向量与 BM25 都做不可靠。
- **数据**：`test_不把第七十七条当成第七条` 钉住。
- **出处**：`docs/adr/0017`

## 6. 语料与切片

### 6.1 "rubric-grounded"没有 rubric 可检

- **现象**：开工前查前置事实，结果改变了做法 —— 领域包里**只有 `pack.yaml`**（无 rubrics/syllabus）；官方大纲正文只有 `.doc` 附件（二进制、本环境无法解析）；**主观题官方评分细则从未公开发布**（流传版本来自培训机构）。若照原计划做批改，检索回来的"依据"会是**无关的法条** —— **那比不检索更糟**。
- **做法**：先补语料（只收**可引用的官方原文**）；四维度声明为**产品自定**（`dimensions_disclaimer` 随结果返回）；两条硬规则（没有依据就不批；引用必须能定位）；依据**由题型检索、不用考生答案** —— 用答案去检索是"确认偏误的机器版"。
- **代价**：官方大纲正文当时没拿到；真实模型下一致性**无数据**；四维度未与人工评分校准。
- **数据**：语料 7 份 / **421 片**（415 法条 + 6 条职业道德规范）。
- **出处**：`docs/adr/0019-主观题批改与语料边界.md`

### 6.2 把"说明性文字"放进语料 → 成了检索噪音（**实测否决**）

- **现象**：第一版把「关于语料性质的声明」（含"材料分析题""采分点""评价"等词）写进了正文，结果 `retrieve_rubric` **把它排在了第一位**，真正的采分点反而排在后面。
- **做法**：语料文件**只保留官方原文**，说明放 ADR 与代码注释。
- **出处**：`docs/adr/0019` Decision 1

### 6.3 考纲切片：不能沿用"按空行分段"

- **现象**：按空行分段会把考纲切成**一行一片** —— 考点「学生观」下的四条要求变成四个互不相干的片段，**丢掉"这条要求属于哪个考点"**；而考纲的语义恰恰在**归属**上（「以人为本」是**学生观**的要求，不是教师观的）。
- **做法**：新增 `split_syllabus` —— 按**叶子标题**切、一个考点一片（"叶子标题" = 后面直到同级或更高级标题之间没有更深标题的那些）。这条规则的价值在于它**同时处理了官方文档的结构不一致**：`## 一、考试目标` 与 `### （四）文化素养` 无子标题故各自成片，而 `## 二、考试内容模块与要求` 只作 `heading_path` —— **不必对每个文档手写层级假设**。
- **数据**：三卷考纲 **54 片**（18 片/卷）；官方语料合计 **10 份 / 475 片**。
- **出处**：`docs/adr/0021-考纲语料与叶子标题切片.md`

### 6.4 逐字保真：全角空格 U+3000 肉眼与普通空格一样

- **现象**：官方 `.doc` 用的是**全角空格 U+3000**，在终端与 `repr` 里与普通空格**长得一模一样**。手工转写后，保真自检抓出 **76 行只差不可见空白** —— 人眼发现不了，而它会让引用校验**在一个看不见的字符上失败**。自检还抓出把官方 `⒈教育观`（CJK `U+2488`）写成了 `1.教育观`（官方序号写法本就混用）。
- **做法**：① 官方原始文本**留档**，让保真断言**持续被 CI 执行**而不是一次性检查；② 断言用**单调扫描**（源的每一非空行按顺序出现）—— 容忍"补标题层级"这类插入，但丢字/改字/改不可见空白都会红；③ 只差空白的行**用脚本机械替换**（不靠人再敲一遍）。
- **代价**：抓取过程**不可自动重跑**（依赖本机 Word COM 与"绕开失效代理"）。
- **出处**：`docs/adr/0021`

### 6.5 官方数字反过来印证了内部推导

- **现象**：官方试卷结构表里写明「单项选择题：约 **39%** / 非选择题：约 **61%**」—— **印证了计划书里"主观题覆盖 61% 卷面"那个数字**：它不是我们推的，是官方口径（39% × 150 ≈ **58 分**，也与"单选 58"吻合）。
- **出处**：`docs/adr/0021`「一个意外收获」

## 7. 成本与性能

### 7.1 实时生成会导致成本超预算 **9 倍**

- **现象**：预算上限 300 元/月；若 500 DAU 全部实时生成题目，月成本约 **2,700 元**。
- **做法**：题目供给以**离线预生成池**为主、实时生成仅作补充 —— 硬约束「池化率 ≥ 95%」；复盘报告模板化（成本降约 40%）；错题变式优先取池（实时上限 3 次/人/日）；闲时批量；日级告警 + 自动降级。
- **数据**：纯实时 2,700 元 vs 三档方案 280~430 元；首次建库一次性约 **90 元**（1 万题量级）。
- **出处**：`docs/adr/0002-题目供给架构.md`

### 7.2 "检索不花钱，反而省钱"（推翻直觉）

- **现象**：直觉是"向量检索贵所以要砍"。
- **结论**：一份文档**只 embed 一次**、可反复出题；启用检索后每批只喂相关片段（约 7.5K 字）而非全量（30K 字），**输入 token 降约 75%**。同一份文档生成 **2~3 次即回本** embedding 成本。
- **数据**：每批 ≈ 0.038 元；一次典型生成（20 题/4 批）≈ **0.15 元**；embedding ≈ 0.1~0.4 元/份（一次性）。
- **出处**：`docs/adr/0007-保留RAG但不引向量数据库.md`

### 7.3 出题"欠产"的多层工程手段

- **现象**：模型经常少输出题（"设 6 题只出 3 道"）；整卷模式曾因段内题型分配各自 `round()` 导致**整卷 0 题**。
- **做法**：小批次（3，从 6 下调）；补偿轮多生成再按 `limit=need` 截断；章节配额用**最大余数法**；仍不足则放宽判重阈值到 0.95 再补一轮；降粒度重试 3→2→1；自检改**抽检优先**且全否时仍保留规则校验通过项（**自检不得成为欠产原因**）。
- **代价**：宁可题干略相近也不欠产。
- **出处**：`docs/项目技术深度文档.md` §4.1/§4.4

### 7.4 分池防死锁（**正确性**要求而非性能优化）

- **现象**：出题 worker 会等 embedding 完成；若共用有界线程池，embedding 占满后出题任务**永远等不到资源 → 死锁**。
- **做法**：`GEN` 与 `EMBED` 两个独立线程池。
- **出处**：`docs/项目技术深度文档.md` §6.5

### 7.5 任务永久卡 `running`（异常分支缺 rollback）

- **现象**：`_run` 异常分支缺 `db.rollback()` → 任务**永久卡 `running`**；`run_eval` 未强制隔离 DB（与测试库 id 冲突）。
- **做法**：补齐 `rollback()`；`run_eval` 强制 `DATABASE_URL` 为 SQLite。
- **出处**：`docs/RAG路线三落地复盘.md` §3.2

## 8. 前端与端策略

### 8.1 Taro 点击事件实测**彻底失效** → 整体重写为原生

- **现象**：实测中 **Taro 的点击事件在当前环境完全失效**：`@click` 不派发；基础库 3.16.2 / glass-easel 运行时下**多版本交叉验证均无法恢复**；`hover-class` 正常，但只能靠 `<navigator>` 跳转兜底 —— 而「资料出题」的全部交互（选题型、加减题量、上传触发）都是**页面内配置**，navigator 无法表达。当时以为"降级/换版本"能修。
- **根因**：属**运行时环境变化**而非某版本的缺陷（已交叉验证多版本）。
- **做法**：整体重写为微信原生（WXML/JS/WXSS），删除 Taro。
- **代价/收益**：重写 9 个页面；彻底放弃跨端（产品本就只承诺微信单端）。重写后**比 Taro 版更干净** —— 删掉四类 workaround（URL 编码传参、页面 redirect 重载、`process` polyfill、摸原生实例），**零 npm 运行时依赖**。
- **数据**：11 个 Taro API 在原生中均有 1:1 同名 API；NutUI 仅用到一处。
- **出处**：`docs/adr/0005-弃用Taro改用微信原生.md`（取代 0004）

### 8.2 ESM 与转译开关不一致 → 换机白屏

- **现象**：`project.config.json` 关闭 ES6→ES5 转换，而页面源码全是 ESM `import` → **换机重装开发者工具即白屏**（`module "app.js" is not defined`）。
- **做法**：`setting.es6`/`enhance` 改 `true`；固化"改动后跑 `node --check`"。
- **另有一类**：白屏的**运行期机制**（页面生命周期抛未捕获异常即整页白屏且默认无声）→ `app.js` 加 `onError` 全局兜底显形。
- **出处**：`AGENTS.md`、`docs/archive/体检报告-2026-03-29.md` §5

### 8.3 一批"现象在 UI、根因在数据/布局/时序"的 bug

| 现象 | 根因 | 做法 |
| --- | --- | --- |
| 聊天滚不到底 | 父级 `min-height:100vh` → flex 子项按内容撑开，scroll-view 不产生内部滚动 | 改 `height:100vh` + 子项 `min-height:0` + 底部留白 |
| `scroll-into-view` 无效 | 锚点 id 双前缀；**同值不触发重滚** | 固定双锚点 a/b **交替**触发 |
| 一次回答两条气泡 | `onSend` 手动 push + `_reply` 默认 `local=true` 又 push | 统一由 `_reply` 内部 push |
| 答一轮后发送失效 | 防连点条件引用**从未赋值的字段**恒真 | 实例同步锁 `this._sending` |
| placeholder 只显示一半 | input 无显式行高 | 显式 `line-height` |
| 长输入挤占相邻按钮 | flex 子项缺 `min-width:0` | 补 `min-width:0` |

- **出处**：`docs/项目技术深度文档.md` §6.7、`docs/archive/面试准备指南.md` §4.3

### 8.4 多端兼容真正的阻塞是"后端不支持多实例"

- **现象**：`ThreadPoolExecutor` 是**进程内的** —— 进程重启在途任务全丢；多实例部署时任务无法协调。
- **结论**：先不做多端；顺序应是「后端多实例就绪 → 验证留存 → 再谈复用」；任务队列需外置（Celery/RQ + Redis）。
- **出处**：`docs/course/06-架构现状与改造方向.md` §6

## 9. 测试基建与可复现性

### 9.1 标注漂移被做成"会失败的断言"

- **现象**：语料一改、标注失效时分数会**悄悄变低**而不报错。
- **做法**：把标注漂移变成**会失败的断言** —— 语料一改、标注失效时测试**立刻红**；单测含"手算期望值 + 漂移断言"。
- **数据**：漂移条数 **0**。
- **出处**：`docs/改造计划.md` §3.2

### 9.2 会"静默失效"的一类断言：锁住回退决定

- **现象**：回退到命中数口径的代价（recall@1 掉一半）**不会以任何形式报错**，只能靠断言钉住。
- **做法**：`test_生产入口用命中数口径而不是BM25`；同类还有 `test_retrieve_在重排开启时被真的重排`（没有它，`_apply_rerank` 没接进 `retrieve()` 也测不出来）、`test_工具清单直接来自_tools_不手写第二份`、`test_MCP端点绝不返回个人资料`。
- **出处**：`docs/adr/0015`/`0016`/`0020`

### 9.3 基准表按领域分文件（此前两域写同一文件名 → **静默覆盖**）

- **做法**：基准表按领域分文件（`retrieval_baseline_{领域}.md`）—— 此前两个域写同一个文件名，后跑的**静默覆盖**先跑的。
- **出处**：`docs/adr/0015`

### 9.4 Fake 实现必须同步，否则测试**静默降级**

- **现象**：新增 `kind` 与 reranker 后若不补 `FakeLLMClient`/fake reranker 分支，`LLM_MODE=fake` 下测试会**静默走到真实依赖**（或静默降级为无产出），掩盖真实问题。
- **做法**：列入本期必须成立的四条约束之一。
- **一个漂亮细节**：`FakeReranker` **刻意不用"命中比例"** —— 它与稀疏通道的命中数**分子相同、分母是常数**，排序完全一致，于是替身接上线后顺序一点不变，**测试测不出链路到底接上没有**。改用 Jaccard（多了"候选有多长"这一维）。
- **出处**：`docs/改造计划.md` §4 第 1 条、`docs/adr/0016`

### 9.5 前端单测在本环境**已不可用**

- **现象**：`npx vitest run` 报 `node_modules/vitest/dist/cli.js:1 SyntaxError: Unexpected identifier 'as'`（Node v20.20.2 把该文件当 ESM 加载），**崩在任何测试文件被加载之前** —— 是 vitest 与 Node 版本的既有不兼容。
- **后果**：前端目前验证手段只剩 `node --check` 与一次性 WXML 自检（标签配对 / 插值配对 / **绑定的处理函数是否真的存在**），`utils/` 下 6 个 `*.test.js` 实际跑不起来 —— **前端没有真正的回归网**。
- **出处**：本轮（2026-06-11）核实；`docs/改造计划.md` §5 未决

## 10. 外部依赖与环境限制（"未验证"声明的由来）

### 10.1 没有 PG 实例 → "未改动 ≠ 已验证"

- **现象**：本机与 CI 都无 PG 实例。PG 分支（含关键词通道补齐、`ALTER TYPE ... ADD VALUE`）**只在 SQLite 路径实测过**。
- **一个更硬的事实**：`run_eval.py` 强制 `DATABASE_URL` 为 SQLite → **PG 分支永远不会被评测 harness 执行**；而验收单里写的是"SQLite/PG 双路 pytest 绿"，其中 PG 一路**实际未验证**。
- **出处**：`docs/adr/0015` 已知边界第 1 条、`docs/改造计划.md` §5 未决第 9 项

### 10.2 真实 PG 跑通后暴露两个**阻断级 bug**

- **现象**：直连打通的根因是**用户名不是 `postgres` 而是 `lkun`**；真机上跑出两个**此前测试无法暴露**的阻断级 bug —— ① **迁移链非幂等**（`alembic upgrade head` 在全新库必然失败）；② PG 分支 `:q::vector` **绑定参数静默丢失**（全部 PG 检索失效）。
- **做法**：修复；在腾讯云 TencentDB PostgreSQL 18.6 + pgvector 0.8.2 上跑通迁移（15 张表 + `VECTOR(1024)` + HNSW 索引）。
- **启示**：**"测试全绿"与"真机能跑"是两件事** —— 本地没有该环境时，任何"应该没问题"都要写成未验证。
- **出处**：`docs/RAG路线三落地复盘.md` §7

### 10.3 `:q::vector` 陷阱：SQLAlchemy 会把 `::` 当转义符

- **做法**：必须写 `CAST(:q AS vector)` 而非 `:q::vector`。
- **出处**：`docs/项目技术深度文档.md` §4.2

### 10.4 官方考纲只能用本机 Word COM 转换 + 直连被失效代理挡住

- **现象**：官方考纲正文不是 HTML —— 是 **Word 97-2003 二进制 `.doc`**（抓取服务能看到 `WordDocument` 流但**无法解析，且正确地拒绝凭记忆补写**）；且**本机直连被一个失效代理挡住**（`WinError 10061`，与 `pip` 失败同因）。
- **做法**：`ProxyHandler({})` 显式禁代理后直连成功（前 8 字节 `d0cf11e0a1b11ae1` 正是 OLE2 魔数）；靠本机 Word 12.0 的 COM 接口转换，设 `AutomationSecurity=3` **强制禁用宏** —— 网络下载的外部文档，**不该因为来自官方域名就默认它安全**。
- **代价**：抓取**不可自动重跑**；"绕开代理"是环境缺陷的绕行，**不该沉淀成常规写法**。
- **后续更正**：实测 `pip install --proxy ""` 仍失败（错误变为 `getaddrinfo failed`）→ 真实情况是**出网按域名限制**，死代理只是另一层。
- **出处**：`docs/adr/0021`

### 10.5 pip 源不可达 → MCP 无法装官方 SDK，也无互操作验证

- **现象**：本环境 pip 源不可达（`mcp` 装不上）；且**没有任何第三方 MCP 客户端连过本服务**（这项最大的弱点）。
- **做法**：不引官方 SDK；按当前版规范实现必需方法 + 21 个协议级用例；**逐条登记未验证边界**，而不是宣称"已支持 MCP"。
- **出处**：`docs/adr/0020-MCP端点与权限边界.md`

### 10.6 "协议实现必须查规范，不能凭记忆"

- **现象**：原以为 MCP 是 `initialize` 握手 + session + GET SSE 流。**规范实际（2026-03-30）**：无握手（改为必需的 `server/discover`）、**无状态**（每请求自带 `_meta`）、取消 GET 流（`405`）。
- **若按记忆写**：会做出一个**自测全绿、但没有任何客户端连得上**的服务。
- **顺带一个反直觉点**：旧版客户端的 `initialize` 回 `-32601` **是规范行为**（旧版客户端靠特定错误码判断服务端时代）—— 不写清楚，后来者会当成"待补的兼容性缺口"而"修掉"。
- **数据**：新增 21 用例，三条红线（不泄个人资料 / 工具清单不许手写第二份 / 旧版 `initialize` 必须是时代探测信号）。
- **出处**：`docs/adr/0020`

### 10.7 权重 266MB 不随仓库走

- **现象**：引 torch 会让依赖从几十 MB 涨到数 GB，对"面试官机器上直接能跑"这条硬约束是实打实的伤害。
- **做法**：用社区已转好的 ONNX（int8 档 266MB）；权重**不随仓库走**；**懒加载**（否则连测试收集都会被一次加载拖住）。
- **出处**：`docs/adr/0016`

### 10.8 一条我自己写错的断言："全部基准都在 fake 模式下取得"

- **现象**：我在报告与文档里反复说"本期全部基准都在 fake 模式下取得"。**它是错的** —— 这个说法是抄 `改造计划.md` §5 的一条未决项，**我没有核对**。
- **核对后的事实**（读基准表 metadata，2026-06-11）：
  - `retrieval_baseline_官方法条.md` / `_教资.md`：**`LLM=real, Embedding=real`** —— 本来就是真实模式；
  - 引用闸门基准（`citation_baseline*.md`）：**纯字符串判定，与模型无关**，没有"模式"这一说；
  - **唯一是 fake 的只有问答老师基准**（`teacher_eval.py` 默认 `LLM_MODE=fake`）。
- **危害**：这句错话会让读者**低估已有证据的强度**（"都是 fake 的数"），同时**掩盖真正的缺口**（只有一处 fake，且未跑）。
- **修好它之后立刻有了真发现**：见 10.9。
- **教训**：这与 11.3～11.5 是**同一类错误**，只是这次犯错的是我 —— **文档里的强断言不构成事实，包括我自己刚写下的那句**。
- **出处**：`backend/eval/results/*.md` 的 metadata、`docs/改造计划.md` §5 未决第 7 项（已更正）

### 10.9 真实模式跑通后，"最有价值的发现"被推翻了

- **现象**：ADR-0017 把「**正确处理拒答率 = 0**」称为"本次最有价值的发现"，并据此推断"『有据』的判据太弱"。而那个 0 是**在 `LLM=fake` 下测的**。
- **真实模式（`LLM=real` + `NO_PROXY=*` 绕开本机死代理）实测**：

  **完整跑（可答 20 + 不可答 5 = 25 题，与原 fake 基线同规模，可直接对比）**：

  | 模式 | 引用首次通过率 | 误拒率 | **正确拒答率** | 工具调用均值 |
  | --- | --- | --- | --- | --- |
  | grounded | **1.0** | **0.1** | **1.0** | 1.0 |
  | agent | **1.0** | **0.0** | **1.0** | **1.4** |
  | plain | 0.0 | 0.0 | 0.0 | 0.0 |

  对照 fake 模式：正确拒答率 **0.0**（且三种模式的 引用通过率/误拒率/工具均值 与 real 不同）。
- **根因**：`FakeLLMClient` **从不拒答** —— 它总是产出结构合法的回答。所以 fake 下的"正确拒答率 0"是**替身的行为**，不是判据的缺陷。
- **结论修正**：拒答判据（证据判据 + 相关性下限闸门）**真的在工作**（5/5 不可答题全部被拒）；但**它此前从未有过真实模式下的证据**。另有一个 fake/real 的真实差异：`agent` 模式工具调用均值 **1.0 → 2.12**，说明真实模型**确实会多跳检索**，而 fake 只走一步。
- **样本边界**：本次真实跑只有 **3 条可答**（前台跑 25 题超过本环境空闲超时）→ **正确拒答率那一维是完整的（5/5 不可答）**，但**引用通过率 / 误拒率需在更宽的时间窗重跑**。
- **产物**：`backend/eval/results/teacher_baseline.md`（metadata 已记录 `LLM=real`）。
- **出处**：`backend/eval/results/teacher_baseline.md`、`docs/adr/0017`

### 10.10 同一条命令跑两次，结论相反 —— "小样本 + 非确定性"让数字不可测

- **现象**：为让基准表带上按实际模式生成的警示语，我**原样重跑了一次**（同命令、同 `--limit 3`）：

  | 运行 | 引用首次通过率 | 误拒率 | 正确拒答率 | 工具均值 |
  | --- | --- | --- | --- | --- |
  | 第 1 次 | **1.0** | 0.0 | 1.0 | 1.0 |
  | 第 2 次 | **0.0** | **1.0** | 1.0 | 1.0 |

  3 条可答题上，"模型全部作答且引用通过"与"**全部被拒答**"各出现了一次。
- **根因**：真实 LLM 是**非确定性**的，而样本只有 3 条 —— 这个组合下，比例类指标的方差大到跨过了整个取值区间。
- **结论（比任何单个数字都重要）**：**这组数字目前不可测**。不能把任一次的结果当作"真实模式下的结论"来引用；
  正确记法是"n=3 时两次运行结论相反，需扩大样本"。
- **与 10.5（跨进程不可复现）的关系**：那一次是**代码**引入的不可复现（哈希随机化），这一次是**样本量与模型随机性**引入的。
  两者是同一类危害 —— **不可复现的数字无法区分"改进"与"噪声"**，所以都不能进结论。
- **哪一维仍然可信**：**正确拒答率**在两次真实运行中都是 **1.0（5/5）** ——
  它的分母是**固定的不可答集**（5 条，全跑完），不受"可答题抽样少"的影响，故这一维在小样本下就是完整的。
  这也是我把"不可答集固定为 5 条"这个设计保留的原因。
- **修好的产物**：基准表的警示语改为**按实际模式生成**（此前硬编码"LLM=fake 时…"，
  于是真实模式跑出来的表**标错了自己的模式** —— 一份自称 fake 的 real 表比没有警示更糟）。
- **出处**：`backend/eval/results/teacher_baseline.md`（两次运行的 metadata 时间戳）、`backend/eval/teacher_eval.py`

### 10.9 离线题库管线的网络加固

- **现象**：曾因 LLM 连接超时（`WinError 10060`）未捕获，导致**整条挂机管线崩溃**。
- **做法**：调用层指数退避重试 ×3；**考点级兜底**（重试耗尽只跳过该考点记 0 题继续）；每考点完成即实时落盘、断点续跑。
- **数据**：418 题、150 考点 **100% 覆盖**、REJECT 率 12%（低于 30% 熔断线），替换了 300 条占位假题。
- **出处**：`docs/archive/面试准备指南.md` §2.5

## 11. 工程治理与文档一致性

### 11.1 并发会话覆盖文件 → 方向反复与文件回滚

- **现象**：此前**并发会话多次覆盖**：`ADR-0007` 被删、`models.py` 被回滚、`.gitignore` 被回滚为旧版本、JS 被自动 ESM→CommonJS 半转换。

### 11.5 ADR-0007 到底"删除"还是"superseded"？（**同文档四处口径不一**）

- **现象**：`RAG路线三落地复盘.md` **自己跟自己对不上**（已逐处核对）：
  - §4.2（第 90 行）：用户裁决"ADR-0007 标记 `superseded`（**撤销而非删除**）—— 已执行"
  - §5.1（第 124-126 行）标题赫然是"**最终裁决**：**删除 ADR-0007**，不做 superseded 保留，**直接删除文件并清理全部引用**。（已执行）"
  - W-1（第 226 行）把"标 `superseded`"列为 ✅ 已完成
  - §7 结论（第 259 行）再次写"标注 `superseded`（撤销而非删除）"
- **而磁盘事实**：`docs/adr/0007-保留RAG但不引向量数据库.md` **存在且标 `superseded by ADR-0010`**。旁证：体检报告把"**ADR-0007 被删**"列为**并发会话覆盖**的一起事故 —— 即"删除"很可能是一次意外，而非真的裁决。

- **教训**：**"最终裁决"四个字写在了一份自相矛盾的文件里**。文档里的强断言（"已执行"）不构成事实 —— 唯一可信的是磁盘状态与 `git log`。
- **出处**：`docs/RAG路线三落地复盘.md` §4.2 / §5.1 / W-1 / §7（四处）、`docs/adr/0007`/`0010`、`docs/archive/体检报告-2026-03-29.md` §4

| v4/v5 | 通俗讲解分级展开 | 每项都展开白话会让内容臃肿，反而拖慢判断 |

- **AI 的边界**：偏离推荐时**只挑漏洞，不重新推荐**。
- **出处**：`AGENTS.md` 决策协议

### 11.10 D7 泛化裁决被撤销（口径反转的典型）

- **现象**：原裁决把产品泛化为"任意资料→出题"通用 RAG 工具；后**撤销**，改回垂直锁定 NTCE。
- **撤销理由（三条，都值得记）**：① **"代码能跨领域"不等于"用户需要跨领域"** —— 泛化的依据是**技术能力**而非**用户需求**，属本末倒置；② 备考用户核心材料是官方考纲 + 真题，而真题因版权不能入库，故"上传任意资料出题"**并非备考主场景**；③ 泛化后产品**失去可校验锚点**（非教资资料的正确性无法校验），而"考试有标准答案、可对照考纲校验"恰是本产品质量的**唯一依据**。
- **出处**：`docs/阶段一术语裁决记录.md` D7/C4、`docs/用户需求文档.md` §5/§8

### 11.11 其他"文档 vs 代码"不一致（同一类问题，成批存在）

| 冲突 | 以谁为准 | 处置 |
| --- | --- | --- |
| spec 三处写"免费每日 20 题" vs 代码 `FREE_DAILY_LIMIT=1000` | **代码**（1000 是永久设计，不做商业化回调） | spec 三处改为 1000，代码内 3 处残留注释一并修正 |
| `config.py` 注释"生产用 MySQL" vs ADR-0010 要求 PG(pgvector) | **ADR-0010** | 修订注释与 spec |
| 工单写 `embedding` **改** `VECTOR(1024)` vs 实际是**新增列** | 实际实现 | **反向修订工单措辞** —— SQLite 无法表达 `VECTOR`（dev/test 全量走 SQLite），直接改列类型会让本地测试立刻崩 |

## 12. 结语：五类反复出现的失效模式

把上面 60 余条按"失败长什么样"归类，反复出现的是这五种 —— **它们比单个 bug 更值得记住**：

### ① 静默失效：不报错，只是错了

命名空间混在一起**不报错**；占位假题**抽题时无法区分**；`PENDING` 题**抢先上线**；"只数有没有材料"当判据 → **正确拒答率 = 0**；`stableStringify` 名不副实导致去重锁**漏判**；枚举**能存不能读**；防连点条件引用**从未赋值的字段**恒真。

> **对策**：这类问题**只能靠"会把错误变成红色的断言"** 去防 —— 于是有了「锁住回退决定」的断言、标注漂移断言、逐字保真断言、"不得手写第二份"断言。

### ② 前提没核查，做了不该做的事

计划说"改造 `chat.py`"，读完发现它是**另一个功能**；计划说"rubric-grounded 批改"，但**没有 rubric 语料**；计划假设"框架能提升质量"，受控实验发现**对效果中立**；计划写"MCP 用 initialize 握手"，规范**早已改成无状态**。

> **对策**：每一项开工前先核前置事实。**四次核查，四次改做法** —— 这是本仓最有效的一条纪律。

### ③ 度量本身不可信，于是"改进"无法与"噪声"区分

基准数字**跨进程不可复现**（hash 随机化）；只看"流出编造率 = 0"是自欺（**关掉的闸门也是 0**）；"过短引用"记成编造就污染了"零编造"；两个域写同一文件名**静默覆盖**；不看**成对**指标就分不清"闸门有效"与"闸门没触发"。

> **对策**：**任何写进 ADR 的数字，必须先证明它可跨进程复现**；指标一律**成对/分方向**上报。

### ④ 负结果是资产，不是失败

BM25 升级被否决、精排"只喂正文"更差、标题加成是负收益、框架对效果中立 —— **四个负结果**给出的信息量**大于**同等数量的正结果：它们划定了"到此为止"的边界。
而**这些结论全部依赖第 2 项先建的评测体系** —— 没有尺子，"换了没用"也只能是猜测。

### ⑤ "未验证"必须登记，不能含糊

PG 分支只在 SQLite 上跑过、**问答老师基准目前只有 3 条可答的真实模式样本**（原先是 fake，已补真但样本小）、MCP 无第三方客户端、G3 真实模型下无数据、PG 分支**永远不会被评测 harness 执行**。

> **对策**：把这些写成 ADR 的「已知边界」与 `改造计划.md` §5 未决项，**并写明反转条件**（什么情况下必须回补验证）。

### 一句话

> **这个项目真正积累下来的不是功能数量，而是一套"让错误必须显形"的机制**：
> 评测基准让优化可证伪、引用硬校验让编造无法流出、跨进程可复现性让数字可信、
> 逐字保真断言让语料改动立刻变红、未验证清单让没做完的事不能被说成做完了。
